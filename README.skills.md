# Реестр корпоративных скиллов

В dashboard появилась вкладка **«Скиллы»**: реестр, Git-источники, история синхронизации
и подключение клиентов. Независимый FastMCP-сервер доступен по `/skills/mcp`. Он работает
в существующем HTTP-процессе с общими TLS и авторизацией, но имеет собственные инструменты,
инструкции и хранилище. RAG endpoint `/mcp` не получает tools или содержимое скиллов.

## Настройка сервера

```dotenv
KB_SKILLS_REGISTRY_ENABLED=true
KB_SKILLS_REGISTRY_DIR=./.cache/skills-registry
KB_SKILLS_MCP_PATH=/skills/mcp
```

После изменения кода или настроек перезапустите backend. Для production UI выполните
`npm --prefix apps/dashboard run build`. Запуск остаётся прежним:
`./scripts/start-backend.sh`. Отдельный клиентский процесс или wrapper не требуется.
Dev-сервер Vite проксирует `/skills/mcp` на backend. Если endpoint изменён, передайте frontend
тот же путь через `VITE_SKILLS_MCP_PATH` или экспортированный `KB_SKILLS_MCP_PATH`.

В **«Скиллы → Источники»** добавьте один или несколько источников:

| Поле | Значение |
| --- | --- |
| Название | Понятное имя команды/набора |
| Git URL | HTTPS, SSH или `file:///absolute/path/to/repository` на сервере |
| Ref | Ветка, тег или commit; по умолчанию `HEAD` |
| Путь | Каталог относительно корня checkout, например `skills`, `ai/skills` или `.` |
| Рекурсивный поиск | Искать пакеты также во вложенных каталогах |
| Интервал | Минуты между проверками; `0` — только вручную |
| Автопубликация | Делать изменившиеся версии доступными клиентам сразу после проверки |
| Включён | Разрешить проверки по расписанию |

**«Проверить»** предварительно клонирует репозиторий и показывает найденные скиллы, не сохраняя
источник. **«Синхронизировать»** ставит фоновую задачу. Новый включённый источник с ненулевым
интервалом проверяется сразу после сохранения. Сервер должен быть запущен для работы расписания;
после простоя просроченные проверки выполняются при старте. При ошибках интервал повторных
попыток увеличивается. Параллельные запросы синхронизации одного источника объединяются.

Git-учётные данные настраиваются на сервере через SSH/credential helper. Пароли и токены в URL
не принимаются и не включаются в клиентские конфигурации. Для локального источника используется
`file://`: в реестр попадает закоммиченная версия, а не незакоммиченные файлы рабочего каталога.
Git submodules не загружаются автоматически. Закреплённый commit проверяется, но сам по себе
не движется на новые коммиты; для обновлений выбирайте ветку.

## Пакеты и версии

Пакет — каталог с `SKILL.md`, содержащим YAML frontmatter `name` и `description`, и всеми
сопутствующими файлами. Например:

```text
skills/
  review-service/
    SKILL.md
    references/checklist.md
```

Имя скилла состоит из строчных латинских букв, цифр и одиночных дефисов, длина 1–64 символа.
Символические ссылки, выход за корень пакета и непереносимые пути отклоняются. Ограничения:
200 скиллов и 64 MiB на источник, 256 файлов на пакет, 2 MiB на файл и 16 MiB на пакет. Код из репозиториев
при импорте не исполняется.

Идентификатор скилла — ID источника и относительный путь пакета. `revision` — SHA-256 манифеста
всех файлов с их путями, хешами, размерами и executable-флагами. Изменение reference-файла также
создаёт новую ревизию. Отдельно сохраняются последовательный номер версии и исходный Git commit.
Повторная проверка без изменений не создаёт новую версию. Возврат к уже известному содержимому
использует существующую ревизию.

В **«Реестре»** доступны файлы, история версий и diff. При выключенной автопубликации администратор
публикует выбранную версию вручную. **Откат** меняет указатель опубликованной версии на сохранённую
старую ревизию. Следующая проверка без изменений не отменяет ручной откат; новое изменение пакета
может быть опубликовано автоматически, если эта настройка включена.

Ошибка разбора одного пакета больше не отменяет обновление всего источника. Корректные пакеты
сохраняются и публикуются согласно настройкам; проблемные пропускаются с сохранением их прошлых
версий. Проверка получает статус **«С предупреждениями»**. В источнике, предварительной проверке
и журнале доступны количество пропущенных пакетов, путь к файлу и причина. Новому некорректному
пакету версия не создаётся; уже существующий не помечается удалённым из-за ошибки парсинга.
Если некорректный родительский пакет скрыл вложенные скиллы, их предыдущие версии также сохраняются.

Парсер принимает UTF-8 с BOM, пустые строки перед frontmatter, закрывающий маркер `---` или `...`
и даты в дополнительных метаданных. `name` и `description` остаются обязательными строками:
невалидный YAML не исправляется автоматически и отсутствующие значения не выдумываются.
Оригинальные файлы и их хеши сохраняются без преобразований. Ошибки YAML показывают место ошибки
без копирования строк исходника в журнал.

После исправления файла в Git следующая синхронизация повторно проверит пакет; при полностью
корректном источнике предупреждения исчезнут. Проверки с предупреждениями продолжаются по обычному
расписанию. «Успешная проверка» у источника означает последнюю проверку без пропущенных пакетов.
Git-ошибка, отсутствующий каталог, неполный обход или превышение общего лимита по-прежнему
останавливают всю проверку, сохраняя предыдущие опубликованные версии.

Исчезнувший из источника скилл
помечается как выведенный из обращения; история остаётся доступной по точной ревизии. Удаление
источника архивирует его и скиллы, не стирая версии. Файлы клиентов автоматически не удаляются.
Одинаковые имена из разных источников видны в реестре, но не могут попасть в один установочный
набор: локальная директория скилла должна иметь однозначного владельца.

Данные и файлы версий находятся в `registry.sqlite3`; checkout — в `checkouts/` рядом с базой.
Для резервной копии остановите backend и сохраните весь `KB_SKILLS_REGISTRY_DIR` либо используйте
штатный SQLite backup API. История пока сохраняется без автоматической очистки; учитывайте её
рост. Планировщик использует файловую блокировку: один владелец на локальное хранилище, остальные
ASGI workers могут обслуживать запросы. Для нескольких серверов с общим сетевым диском этот
режим не предназначен. Прерванные задачи восстанавливаются после перезапуска.

## Подключение GigaCode

1. При включённом управлении доступами откройте `/connect`, получите MCP-конфиг и выберите
   `corporate-skills` (при необходимости также `corporate-kb`). Готовый конфиг содержит URL
   и личный токен для каждого выбранного сервера. Добавьте выбранные записи в `mcpServers`
   файла `~/.gigacode/settings.json`, сохранив другие настройки, и перезапустите CLI.
   Для режима без управления доступами во вкладке **«Скиллы → Подключение»** доступен
   отдельный URL-конфиг. Он не содержит секретов; если настроен общий Bearer-токен,
   добавьте разрешённый `headers.Authorization` так же, как для основного MCP.
2. Выберите нужные скиллы в реестре. Подготовьте набор для пользователя или проекта.
3. Скопируйте полученный prompt в GigaCode. Он получает выбранные неизменяемые версии через MCP
   и устанавливает их штатными файловыми/терминальными инструментами CLI.
4. Перезапустите GigaCode, чтобы перечитать локальные скиллы.

Подключение `corporate-kb` само по себе не подключает `corporate-skills`. Prompt и ZIP
расширения также не регистрируют MCP-сервер в CLI. Для уже настроенных клиентов нужно один раз
добавить новую запись. Пустой результат `skills_search` означает, что сервер подключён,
но в выбранном реестре ещё нет опубликованных скиллов.

### Полностью локальный MCP через stdio

Если CLI и dashboard работают на одном компьютере, CLI может сама запускать отдельный
Skills MCP без HTTP-посредника. Добавьте в свои настройки:

```json
{
  "mcpServers": {
    "corporate-skills": {
      "command": "/absolute/path/to/project/.venv/bin/python",
      "args": ["-m", "skill_registry.mcp_server"],
      "cwd": "/absolute/path/to/project",
      "env": {
        "PYTHONPATH": "/absolute/path/to/project/src",
        "KB_SKILLS_REGISTRY_DIR": "/absolute/path/to/project/.cache/skills-registry"
      },
      "timeout": 30000,
      "trust": false
    }
  }
}
```

Замените пути своими. `KB_SKILLS_REGISTRY_DIR` должен совпадать с существующим хранилищем dashboard:
несуществующая база даст понятную ошибку запуска; другой существующий каталог даст другой реестр.
Сначала запустите dashboard, добавьте источник и опубликуйте скиллы. Этот процесс читает опубликованные
версии; источники и синхронизацию по-прежнему настраивают в dashboard. Запуск CLI не запускает
Git-проверку или RAG-индексацию. Доступ к локальным данным определяется правами ОС.
Для реестра на другом компьютере используйте HTTP-конфигурацию через `/connect`.

Альтернативная команда сервера — `bash /absolute/path/to/project/scripts/start-skills-mcp.sh`.
Она запускает тот же stdio endpoint из окружения проекта. Установщик
`scripts/install-mcp-server.sh` теперь печатает обе отдельные записи для ручного объединения
с настройками CLI. Его stdio-конфиг читает путь из `.env` установленной копии, не перекрывая его
путём по умолчанию. Сам запуск скрипта сервера не добавляет запись в настройки клиента.

Для следующих обновлений можно вызывать MCP prompt `corporate_skills_sync` или установить
скачиваемый клиентский `SKILL.md` в `~/.gigacode/skills/corporate-skills-sync/SKILL.md` и попросить
GigaCode обновить корпоративные скиллы. Для project scope используется `.gigacode/skills`.
Назначение prompt — проверить существующий `corporate-skills.lock.json`, получить опубликованные
ревизии, проверить хеши и обновить только управляемые пакеты. Он предписывает сохранять локальные
правки и чужие файлы, сообщать о конфликтах, устанавливать через временный каталог с резервной
копией и обновлять lock только после успеха. Это инструкции клиентской модели; сервер не может
проверить, выполнила ли конкретная CLI все шаги, и не считает скачивание подтверждением установки.

Также доступен воспроизводимый ZIP с `gigacode-extension.json`, выбранными скиллами и lock-файлом.
Его установка через native extension manager зависит от версии GigaCode: сначала проверьте
`gigacode extensions install --help`. Поддержка этого формата и upstream Qwen `--auto-update`
в конкретной сборке GigaCode не подтверждена. ZIP фиксирует версии; скачанный архив сам не
становится источником автоматических обновлений. Смешивать установку одного скилла через
extension manager и прямую запись в `.gigacode/skills` не следует.
Для обновления расширения `corporate-skills` формируйте полный желаемый набор его скиллов.

**На сервере обновления обнаруживаются автоматически. На клиенте синхронизация запускается
prompt/скиллом по запросу пользователя.** MCP не записывает файлы на клиентской машине и
не запускает клиент при его закрытии. Клиентских фоновых помощников, wrapper-скриптов или
непроверенных startup hooks здесь нет.

## MCP и доступ

| Tool | Действие |
| --- | --- |
| `skills_search` | Поиск и постраничный список метаданных |
| `skills_get_release` | Манифест; при `file_path` и точной `revision` — один файл |
| `skills_check_updates` | Сравнение установленных ревизий с опубликованными |
| `skills_prepare_install` | Зафиксированный манифест выбранного набора и prompt установки |

Тела скиллов не включаются в discovery и не загружаются автоматически. Подключение отдельного
MCP само по себе не изолирует контекст модели: если клиент подключил оба сервера, он видит
инструменты обоих. Здесь экономия достигается четырьмя короткими tools и загрузкой файлов
по запросу.

REST API dashboard расположен под `/admin/api/skills`: `status`, `sources`, `sources/validate`,
`sources/delete`, `sync`, `jobs`, `registry`, `detail`, `release`, `file`, `diff`, `publish`,
`connect`, `prepare-install`, `client-skill`, `bundle`.

При `KB_ACCESS_ENABLED=true` личный токен/пользовательская сессия позволяют читать реестр
и получать наборы. Изменение источников, запуск Git-проверки и публикация требуют отдельной
административной сессии из `/access-admin`; POST также требует её CSRF-токен. Во вкладке есть
переход к входу администратора. В legacy-режиме управление использует `KB_ADMIN_PASSWORD`,
чтение также доступно с MCP bearer token. Если защита не настроена, локальный режим остаётся
открытым, как основной dashboard.
