# Отдельный модуль «Харнес»

Харнес вынесен в `src/agent_harness`: собственная страница, HTTP API, настройки,
очереди, политика усилия, режим «Автопилот», LangGraph и SQLite. Пакет не импортирует код портала, RAG
или GigaCode. Страница — самостоятельные HTML/CSS/JS без сборки dashboard.

Портал подключает его через один адаптер `corporate_kb.harness_integration`.
Адаптер передаёт авторизацию, доступ к текущим индексам и существующий исполнитель
GigaCode. Направление зависимости: **портал → адаптер → интерфейсы харнеса**.

Харнес и A2A используют один исполнитель GigaCode и его сохранённый вход. Страница
харнеса работает и при выключенном A2A. Дополнительный файл профиля GigaCode ей
не нужен. Инструкция запуска: [GigaCode](README.agent-activation.md).

## Подготовить или обновить одной командой

Из корня полученного репозитория:

```sh
./scripts/setup-harness.sh
```

Команда устанавливает библиотеки в `.venv` и заранее собирает два Docker-образа:
`harness-sandbox:local` для Git/SSH/Python/поиска и
`harness-sandbox-java21:local` с Java 21, `javac` и Maven. Повторный запуск использует
кэш Docker. Установка выполняется при подготовке сервера, а не на каждом вопросе.
Нужны **uv или Python 3.12**, работающий Docker Engine и доступ к реестрам при первой
установке. По умолчанию используется уже установленный uv; если его нет — обычный pip
через `scripts/setup-pip.sh --no-dev`. Сам uv скрипт не скачивает. Для pip нужен Python
3.12 или готовая `.venv` с Python 3.12; при наличии uv недостающий Python 3.12 может
быть установлен автоматически.

**Для корпоративной сети с настроенным pip, прокси или внутренним каталогом пакетов:**

```sh
./scripts/setup-harness.sh --installer pip
```

Этот режим сохраняет настройки pip, включая каталог пакетов, прокси и CA-сертификаты,
не подставляет публичный PyPI и работает даже при отсутствии пакета `uv` в каталоге.
Он устанавливает совместимые версии по ограничениям `pyproject.toml`, **не** точные
версии из `uv.lock`. Во внутреннем каталоге должны быть доступны зависимости проекта
и сборщик `hatchling`; отсутствие этих пакетов остаётся ошибкой установки.

Для точной установки из lock-файла используйте `--installer uv`: требуется уже
установленный uv. При ошибке этого режима скрипт завершится без скрытого переключения
на другой способ установки.

Только обновление библиотек, без сборки образов:

```sh
./scripts/setup-harness.sh --deps-only
# Корпоративный pip без uv:
./scripts/setup-harness.sh --installer pip --deps-only
```

Скрипт не делает `git pull`: сначала получите нужную версию репозитория, затем
запустите команду. В режиме uv используется полученный вместе с кодом `uv.lock`.
Он сохраняет ранее установленные дополнительные пакеты и не устанавливает тяжёлые
semantic extras. После обновления перезапустите backend. Подключения, `.env` и
включение песочниц остаются под управлением администратора в интерфейсе.

Для этой версии обязательны `langchain` и `langchain-text-splitters` вместе с
LangGraph и его SQLite checkpointer. После получения кода выполните
`./scripts/setup-harness.sh --installer pip --deps-only` и перезапустите backend.
Скрипт устанавливает зависимости из проекта; отдельная установка `uv` не требуется.

Отдельный сервер БД для первого запуска **не нужен**: SQLite создаёт файлы внутри
`KB_HARNESS_STATE_DIR`. Это общие файлы экземпляра, с отдельными записями пользователей.
Используйте постоянный локальный каталог на диске и один процесс backend; PostgreSQL
и распределённая очередь понадобятся при переходе к нескольким процессам/репликам.

## Включить или выключить

По умолчанию модуль выключен. В `.env`:

```dotenv
KB_HARNESS_ENABLED=true
KB_HARNESS_STATE_DIR=./var/harness
```

После перезапуска backend отдельная страница доступна на `/harness/`, а в навигации
собранного dashboard появляется ссылка «Харнес». Саму страницу харнеса собирать не нужно.
Она использует личную сессию портала. При старой схеме авторизации можно ввести Bearer
token или пароль администратора в форме страницы; данные остаются в текущей вкладке.

`KB_HARNESS_ENABLED=false` и перезапуск отключают страницу `/harness/`, её API,
собственные workers и создание её хранилища. Это не просто скрытие кнопки.
Агент A2A независимо использует общий runtime из пакета `agent_harness`;
эта настройка не отключает его и не запрещает импорт общего пакета.
При штатной остановке активные работы отменяются; история на диске сохраняется.
Следующее включение снова использует этот каталог. При аварии незавершённые работы
помечаются `interrupted`; доступно явное продолжение из сохранённого состояния LangGraph.

Управление бюджетами вынесено в отдельную страницу `/harness/control/`
(`/control/` при самостоятельном запуске). Флаг `HARNESS_CONTROL_ENABLED=false`
с перезапуском отключает её страницу и API. Работа Harness и ранее сохранённые
ограничения при этом сохраняются. Доступ к данным и изменению настроек есть только
у администратора; оболочка страницы сама по себе не открывает служебные данные.

RAG-адаптер читает выбранные индексы и документы. В режиме исследования дополнительный
`ToolPort` подключает репозитории, исходящие MCP и A2A. Настройки и исполнители лежат
в самом `agent_harness`, без зависимости от основного dashboard. Общая память АС хранит
автоматический опыт запусков всех пользователей, оценки ответов, подтверждённые заметки
и исправления. Подбор учитывает доступ к источникам; личные чаты и черновики не становятся
общими. MCP-вход к харнесу пока не реализован. Веса модели не переобучаются.

## Настройки репозиториев, MCP, A2A и песочниц

Кнопка **«Настройки»** доступна администратору. Настройки общие для экземпляра сервиса
и сохраняются в `KB_HARNESS_STATE_DIR/configuration.sqlite3` с правами `0600`; отдельная БД
под каждого сотрудника не создаётся. У подключения есть ID, название, включатель и
список серверных ID пользователей. Пустой список означает доступ всем вошедшим
пользователям Harness. В портале личный ID имеет вид `user:<id>`.

- **Репозитории:** HTTPS, `ssh://git@host/path` или `git@host:team/repo.git` и ветка,
  тег или commit. SCP-адрес сохраняет путь относительно домашнего каталога SSH-пользователя.
  При исследовании выбранного
  репозитория агент может клонировать его, искать текст, читать строки файлов и
  выполнять команды анализа/сборки/тестов в контейнере. Конкретный commit включается
  в подтверждения; HEAD не объявляется версией, развёрнутой в production.
- **MCP:** Streamable HTTP endpoint и явный список разрешённых инструментов.
  «Проверить» получает настоящий каталог, после чего администратор выбирает инструменты.
  Пустой список запрещает все вызовы. Агент читает схему выбранного инструмента;
  аргументы проверяются по текущей JSON Schema перед выполнением.
- **A2A:** JSON-RPC endpoint протокола 0.3. Проверка читает
  `/.well-known/agent-card.json` на том же origin; адрес из карточки не переопределяет
  сохранённый endpoint. Поддержаны `message/send`, ожидание `tasks/get` и попытка
  `tasks/cancel` при отмене. Удалённый агент получает только сформулированный вопрос.
  Его ответ обозначается как вывод другого агента, а не автоматически доказанный факт.
- **Доступы:** поле токена содержит **имя переменной окружения сервера**, например
  `HARNESS_JIRA_TOKEN`, а не сам токен. Значение передаётся только настроенному endpoint
  как Bearer; для Git — как HTTP Authorization. Адреса с паролями и query запрещены.
  Для соединения с токеном требуется HTTPS. Redirect не переносит credentials.
  stdio MCP и интерактивные OAuth-подключения здесь не поддержаны.

Во вкладке **«SSH-ключи»** администратор добавляет приватный ключ PEM/OpenSSH без
пароля и доверенные строки `known_hosts`, затем выбирает ключ у репозитория.
Проверка ключа сервера строгая: автоматического доверия неизвестному SSH-хосту нет.
Приватный ключ хранится отдельно в `ssh-credentials` (каталог `0700`, файлы `0600`),
не возвращается API и не включается в контекст модели. Он передаётся через stdin
только в tmpfs контейнера клонирования. Анализирующие контейнеры не получают ключ
или SSH-agent. Ключ, на который ссылается репозиторий, нельзя удалить до изменения настройки.

Старый `integrations.json` импортируется в БД один раз при первом запуске новой версии;
последующие изменения читаются из БД. Исходный файл остаётся для резервного восстановления.

## Обнаруженные ресурсы и запросы доступа

Ссылки из пользовательского вопроса и полученных материалов появляются в разделе
**«Обнаруженные»**. Адреса из сгенерированного ответа не считаются обнаружением.
Поиск ссылок не обращается по ним в сеть, не запускает инструмент и не расширяет права.
Ссылки с встроенными HTTP-паролями отвергаются, query и fragment не сохраняются.

Читатель нажимает **«Запросить доступ»**: адрес становится виден администратору в
списке запросов внутри Harness. Сам вопрос и текст документа при этом не передаются.
Администратор открывает заполненный черновик подключения, уточняет тип/адрес,
назначает доступы и сохраняет. Черновик изначально выключен и ограничен автором
запроса. После настройки подключения оно отображается как настроенное; пользователь
выбирает новый источник и продолжает исследование либо создаёт новый запрос.
Произвольная web-ссылка не становится автоматически MCP-сервером или репозиторием.

Сохранение настроек само не запускает внешние действия. Подключения появляются в
области поиска, права и включатели перепроверяются при каждом вызове. **Быстрый режим
использует только RAG**, не клонирует и не запускает MCP/A2A. В исследовании действия
ограничены выбранной областью, усилием, временем и числом вызовов. «Выбрать всё»
выбирает область до 1000 источников; это не обещание опросить каждый источник за один запуск.
MCP allowlist определяет допустимые операции, но не является транзакционным approval UI:
не добавляйте в общий allowlist разрушительные инструменты. Удалённый A2A-сервис
сам отвечает за ограничения собственных действий; локальный timeout не гарантирует
остановку удалённой системы, если она не поддерживает отмену.
Для MCP отмена прекращает локальное ожидание и закрывает соединение; установленный
SDK не отправляет `notifications/cancelled`, поэтому удалённая операция может продолжаться.

## Подготовка песочниц на сервере

Обычная подготовка — `./scripts/setup-harness.sh`: она сразу собирает базовый и Java 21
образы. Если библиотеки уже установлены, образы можно собрать отдельно:

```sh
docker build -t harness-sandbox:local -f src/agent_harness/sandbox.Dockerfile src/agent_harness
docker build -t harness-sandbox-java21:local -f src/agent_harness/sandbox.java21.Dockerfile src/agent_harness
```

Java-образ содержит JDK 21 и Maven, поэтому компиляция отдельных Java-файлов не требует
установки JDK во время исследования. Для сборки конкретного Maven-проекта заранее
добавьте его зависимости и плагины в собственный доверенный образ и настройте доступный
локальный Maven repository. Наличие Maven само по себе не означает, что зависимости
любого проекта уже загружены; команды анализа выполняются без сети.

В **Harness → Настройки → Песочницы** включите песочницы и проверьте базовую среду
`harness-sandbox:local`. В разделе **«Дополнительные среды»** проверьте профиль
**Java 21**: образ `harness-sandbox-java21:local`, профиль включён. Для Java-запроса
выберите **«Исследовать» → «Среда выполнения» → «Java 21»**. Базовый образ при этом
заменять не нужно: профиль задаёт среду отдельного исследования.
Образ автоматически не скачивается (`--pull never`). Если Engine/образ недоступен,
код не выполняется на хосте в обход контейнера. Для другой сборочной среды подготовьте
свой образ с Python 3, Git и OpenSSH client; необходимые зависимости должны быть в образе, поскольку
после клонирования команды работают без сети.

Каждый запрос получает собственные временные тома, привязанные к владельцу и
репозиторию. Рабочие файлы находятся в ограниченном tmpfs, контейнер запускается
не от root, без capabilities, с read-only корнем и лимитами CPU/RAM/PID/времени/вывода.
HOME, каталоги хоста и Docker socket внутрь не монтируются. Сеть есть только на этапе
клонирования; Git hooks, submodules и LFS не запускаются. Команды анализа выполняются
отдельно с `--network none`. По завершении или отмене контейнеры и тома удаляются;
в истории остаются ограниченные результаты и ссылки, а не вся копия репозитория.
После аварийного завершения процесса оставшиеся ресурсы с метками Harness требуют
очистки администратором; автоматический сборщик ресурсов между рестартами пока не заявлен.
Docker изолирует рабочий код, но GigaCode CLI остаётся отдельным доверенным процессом
хоста; его границы описаны в `README.agent-activation.md`.

## Режимы и усилие

- **Быстро:** параллельный поиск по всем выбранным RAG-индексам и один итоговый вызов модели.
  Найденные материалы появляются до готовности объяснения. По умолчанию предел
  выполнения — 120 секунд после выхода из очереди; при его исчерпании начинается
  отмена провайдера, очистка которого может потребовать дополнительного времени.
- **Исследовать:** первичный поиск по всем выбранным RAG-индексам, открытие подходящих
  документов, уточняющие запросы, код и разрешённые внешние инструменты, затем итог.
  Первичный обход не расходует запас уточняющих обращений. Поисковые фрагменты
  одного документа не перезаписывают друг друга. При чтении доступен оригинал
  документа с отдельным лимитом, а не сжатая выдача MCP для быстрых клиентов.
- **Автопилот:** тот же цикл исследования, но модель может обоснованно запросить
  изменение бюджета через `request_budget`: например, дополнительные чтения,
  вызовы модели, время или входной контекст. Сервер применяет запрос только в
  пределах потолков администратора. Запрос, решение и новые значения видны в ходе
  работы. Обычные режимы сами свои бюджеты не расширяют.
- **Усилие:** низкое, обычное, высокое. Меняет лимиты уточняющих обращений, контекста
  и шагов исследования, а также число и размер фрагментов даже при одном индексе.
  Это исполняемая политика сервиса, не неподдерживаемый
  `reasoning_effort` GigaCode. Высокое усилие не гарантирует правильность ответа.
- **Исследовать глубже:** новый связанный запуск с вопросом предыдущего разбора.
  Источники читаются заново; предыдущий ответ не считается подтверждённым фактом.

| Начальные настройки исследования и Автопилота | Низкое | Обычное | Высокое |
| --- | ---: | ---: | ---: |
| Основные вызовы модели, включая итоговый и запросы бюджета | 4 | 8 | 16 |
| Отдельные вызовы модели для сжатия беседы, до | 8 | 8 | 8 |
| Уточняющие обращения после начального обхода | 12 | 24 | 48 |
| Автоматическое чтение найденных документов, до | 1 | 3 | 6 |
| Размер читаемого документа, символов | 12 000 | 20 000 | 32 000 |
| Входной контекст, оценка токенов | 20 000 | 30 000 | 40 000 |
| Максимальное время по умолчанию | 7,5 мин | 15 мин | 30 мин |

Это верхние пределы, а не обязательное число действий. Медленные или недоступные
источники могут не завершить поиск до отведённого времени; счётчик покрытия показывает
фактически опрошенные индексы. Поиск по индексу не означает чтение всех его документов.
История инструментов, ошибки, прошлый опыт и сведения о покрытии передаются модели
и при финальном синтезе. Оценка токенов учитывает сериализованный JSON-запрос,
экранирование кода, историю и описания инструментов. Материал выбирается по
соответствию вопросу и источникам. Точный токенизатор корпоративной модели неизвестен:
используется библиотечный приблизительный подсчёт с настраиваемым коэффициентом.

Начальные таймауты можно задать в `.env`: `HARNESS_QUICK_TIMEOUT_SECONDS=120`,
`HARNESS_INVESTIGATE_TIMEOUT_SECONDS=900` (базовое время обычного усилия),
`HARNESS_FINAL_RESERVE_SECONDS=120`. После сохранения через страницу управления
приоритет имеют настройки из `control.sqlite3`.

Очереди быстрых запросов и исследований разделены. Общие лимиты внешнего провайдера
при этом сохраняются: мгновенный свежий ответ через CLI не обещается. Токенный streaming
не реализован; страница опрашивает статус и показывает реальные готовые данные.

Разговор отображается одной лентой сообщений. Интерфейс открывает последние 200
сообщений и позволяет подгрузить более старые; это размер страницы, а не лимит памяти
модели. Фиксированного ограничения истории в 12 пар сообщений нет. Сжатие по бюджету
токенов описано ниже. История служит контекстом разговора, а актуальные факты проверяются
по источникам заново. Новое сообщение создаёт отдельный запуск с собственными бюджетами
и песочницей при необходимости.

Во время работы видны реальные этапы: планирование, поиск, чтение документа или кода,
вызов песочницы, проверка результатов, уточнение поиска и подготовка ответа. Раздел
хода работы показывает цель, список проверок, оставшиеся вопросы и журнал действий.
Это наблюдаемые действия и краткий план, а не скрытые рассуждения модели.
Просмотр старого ответа не останавливает обновление выполняющегося сообщения.

Без модели поиск работает: результат помечается частичным, показываются найденные
материалы и причина отсутствия синтеза. Вместо анализа не выводится имитация ответа.

## Управление Автопилотом и наблюдение

На странице **«Управление»** задаются профили всех трёх режимов и уровней усилия:
основные вызовы модели, вызовы сжатия, обращения к источникам и инструментам,
параллельность начального поиска, автоматическое чтение документов, размеры материалов,
входной контекст и время. Начальный обход выбранных RAG-индексов учитывается отдельно
от уточняющих обращений; его объём ограничен числом выбранных индексов и общим временем.
Если часть индексов ещё не была опрошена из-за времени, после принятого расширения
Автопилот продолжает начальный обход с этих индексов. Уже опрошенные индексы заново
не обходятся автоматически; ошибки источников остаются видны отдельно.

Для Автопилота отдельно задаются потолки и число разрешённых расширений. По умолчанию
потолок составляет 128 основных вызовов модели, 32 вызова сжатия, 512 уточняющих обращений,
512 инструментов, 2 часа и 60 000 входных токенов; допускается до четырёх расширений.
После первого расширения новое требует появления новых подтверждений, если включена
проверка продвижения. Агент объясняет конкретную следующую проверку; решение принимает
серверная политика. Агент не меняет общие настройки, права, сертификаты или ограничения
контейнеров. Разрешённые дополнительные попытки исправить итоговый ответ задаются
отдельно через `max_answer_retries` и также входят в фактический счётчик вызовов.

Там же доступны параметры контекста и сжатия, очередей, времени авторизации и очистки,
остановки без продвижения, повторных попыток, хранения истории и объёма общей памяти.
Таймаут RAG задаётся отдельно через `source_timeout_seconds`, внешнего инструмента —
через `external_tool_timeout_seconds` (по умолчанию 600 секунд). Общее время запроса
ограничивает оба. `max_decision_errors` задаёт, сколько некорректных решений модели
допускается перед переходом к итоговому ответу; по умолчанию — три.
Профиль и потолки закрепляются в запросе при его постановке в очередь вместе с номером
редакции настроек. Изменения применяются к новым запросам; выполняющийся запрос сохраняет
свой бюджет. Изменение числа обработчиков и размера очередей требует перезапуска backend.
Сохранение настроек защищено от перезаписи чужой более новой редакции.

Графики показывают фактические запуски, состояния, длительность, вызовы модели и
источников, расширения бюджета и сжатия. Оценка токенов и расход, сообщённый API модели,
разделены; отсутствие данных провайдера не выдаётся за нулевой расход. Статистика строится
по сохранённой истории, поэтому удаление и срок хранения влияют на показатели.
Администратор может остановить активный запуск. Эта операция не открывает ему вопрос,
ответ, владельца или материалы личного чата: API возвращает только `id` и `status`.

Административные API относительно корня модуля:
`GET/PUT /api/control/settings`, `GET /api/control/metrics?days=7`,
`POST /api/control/runs/{run_id}/cancel` с телом `{}`. Изменения требуют проверки
прав администратора и защиты от межсайтовых запросов. Бюджеты Harness не увеличивают
физическое окно, rate limits или ограничения GigaCode/корпоративного API.

## Как сжимается беседа

История берётся из личной цепочки сообщений в SQLite с повторной проверкой доступа
ко всем исходным индексам. `SummarizationMiddleware` из LangChain определяет момент
сжатия по оценке токенов, оставляет последние сообщения и вызывает ту же подключённую
модель для смысловой сводки более ранней части. Для длинных сообщений используются
библиотечные средства разбиения текста. Это отдельные учтённые вызовы модели, а не
скрытая бесплатная операция. LangGraph продолжает управлять исследованием и сохранять
его шаги через `AsyncSqliteSaver`; DeepAgents не является движком этого модуля.

По умолчанию оператор задаёт окно 65 536 токенов и резерв ответа 4 096; автоматически
определить реальное окно GigaCode модуль не обещает. Истории отводится 35% входного
бюджета, сжатие начинается при 80% этой доли, свежему хвосту оставляется 35%.
Размер сводки по умолчанию — до 1 024 оценочных токенов. Все эти значения редактируются.
Входной бюджет ограничивается заданным окном за вычетом резерва ответа.

Сводки кэшируются в `runs.sqlite3` отдельно по владельцу и ветке беседы. Перед
повторным использованием проверяются исходные сообщения, область доступа и выбранные
источники. При удалении или истечении срока хранения исходных сообщений соответствующий
кэш удаляется. Сводка не попадает в общую память АС; исходная переписка сохраняется,
сжатие её не переписывает. Ошибка сжатия или исчерпание его бюджета явно показывается;
Автопилот может запросить дополнительный бюджет в пределах разрешённых потолков.
В данных ответа `context_summary` видны размер до/после, число сжатий и использование
кэша. Это оптимизация контекста разговора, а общая память АС хранит опыт разных запусков.

## Включить GigaCode

Используются существующие `KB_GIGACODE_ENABLED=true` и `KB_GIGACODE_COMMAND` с рабочей
командой CLI, как при анализе в портале. После обновления перезапустите backend,
откройте `/harness/` с правами администратора и нажмите **«Включить GigaCode»**.
Если требуется вход, ссылка появляется в карточке модели только администратору.
После готовности можно отправить вопрос. Включение во вкладке A2A также делает
модель доступной харнесу: отдельный повторный запуск не нужен.

Кнопка выключения управляет общим исполнителем и останавливает его вызовы в обоих
модулях. Отключение самой страницы через `KB_HARNESS_ENABLED=false` не отключает A2A.
После перезапуска сервера исполнитель снова ожидает явного включения администратором;
сохранённая CLI-авторизация остаётся. Общие читатели видят состояние, но не URL входа
и события администратора.

`KB_HARNESS_MODEL_PROFILE_PATH` больше не используется страницей и не блокирует её,
даже если содержит старый неверный путь. Отдельный экспериментальный
`GigaCodeChatModel` для LangChain по-прежнему требует явно переданный проверенный
`launch_profile`. Границы обычного CLI-запуска описаны в инструкции GigaCode.
Настоящий корпоративный CLI в среде разработки отсутствует; live-вход проверяется
на сервере, где уже установлен GigaCode.

Передача большого запроса в CLI находится под контролем отмены и таймаута.
После события готового результата исполнитель ограниченно ждёт завершения CLI
и очищает его группу процессов. Поздние ошибки в этом интервале не маскируются успехом.
Пустой или неверно оформленный итог получает одну повторную попытку без повторения
инструментов; известное обрезание генерации также запускает подготовку законченного
ответа. Повторная неудача показывается как ограничение. Разовая ошибка ответа не
сбрасывает рабочую авторизацию GigaCode. Размер ответа по умолчанию — 50 000 символов
(`HARNESS_ANSWER_CHARS`); сокращение по этому ограничению явно помечается.
Повторная попытка остаётся внутри общего таймаута; в быстром режиме она добавляет
второй вызов модели только после ошибки.

## Хранение и пользователи

Личная история и общая память АС живут в `KB_HARNESS_STATE_DIR/runs.sqlite3`, контрольные точки
LangGraph — в `checkpoints.sqlite3`, подключения — в `configuration.sqlite3`, бюджеты —
в `control.sqlite3`, обнаруженные
ссылки — в `discoveries.sqlite3`. Память одна на экземпляр Harness, а не отдельная база
на каждого человека. История и обнаружения разграничены по владельцу. Запуски принадлежат
серверному `owner_id`; браузер не задаёт этот идентификатор. Чтение и отмена чужого
запуска через обычный API возвращают 404. Отдельный административный API позволяет
только остановить чужой запуск без чтения его содержимого. Отозванная личная сессия не даёт читать историю; права
повторно проверяются перед чтением источника и после него.

В текущем портале право читать RAG является общим для авторизованных пользователей;
новая система индивидуальных ACL документов здесь не создаётся. При исчезновении
доступа к индексу сохранённый ответ и его evidence скрываются.

**Память формируется автоматически:** завершённый запуск сохраняет кейс с вопросом,
кратким результатом, найденными документами и использованными инструментами. Ошибки
сохраняются как уроки с типом операции и рекомендацией следующей проверки, без сырых
исключений и аргументов инструментов. Это неподтверждённый опыт (`experience`), который
помогает планировать новый поиск; он не заменяет актуальные источники.

Кнопки **«Помогло» / «Не помогло»** под ответом записывают обратную связь, включая
необязательный комментарий. Отрицательная оценка превращает кейс в урок: прежний ответ
не подставляется в память как решение, модели передаются замечание и необходимость
новой проверки. Положительная оценка также не объявляет ответ доказанным фактом.
Ручные заметки и исправления можно отдельно подтвердить для использования.

При похожем вопросе выбираются до трёх записей по совпадению слов из опыта **всех
пользователей** с учётом прав и выбранных источников. Для использования записи нужен
доступ ко всем её исходным индексам, которые должны входить в выбранную область поиска.
В ответе видны использованные записи; в разделе **«Общая память АС»** видны происхождение,
оценка и общий счётчик использования. Один запуск увеличивает счётчик только один раз,
независимо от автора записи. Редактировать и удалять запись может её автор; черновик видит
только автор, после подтверждения он становится общим. Ссылка на чужой личный чат не выдаётся.
Оценка собственного ответа обновляет общий опыт, который используется другими пользователями.

Повторное использование образует обратную связь: для каждой действительно переданной
модели записи сохраняется результат последующего запуска. Его оценка обновляет общие
счётчики записи (`quality`: `uses`, `helpful`, `unhelpful`, `completed`, `incomplete`).
Повторное сохранение не удваивает счётчики; изменение оценки заменяет предыдущий голос.
Релевантность остаётся главным критерием подбора, оценки помогают выбирать между
близкими записями. Неудачное применение передаётся как предостережение; оно не доказывает
ошибочность самой записи. Завершение запуска также не подтверждает истинность ответа.
Автокейс сохраняет краткий план и названия инструментов. Комментарии и новые материалы
последующего пользователя не копируются в запись с более узкой областью доступа:
туда попадают только агрегированные счётчики. В ответе видно, какой опыт использован
и какой кейс обновлён. После удаления чата накопленная статистика общей записи сохраняется.

Переключатель памяти относится только к текущему пользователю: прекращает автоматическое
пополнение из его запросов и подбор для его ответов, но не отключает память коллег.
Явное ручное сохранение и исправление записей остаётся доступным. Общий лимит — 10 000
записей на экземпляр, без отдельных квот по пользователям. При заполнении старый
автоматический опыт заменяется новым, ручные заметки не вытесняются. Интерфейс показывает
по 200 доступных записей; кнопка «Показать ещё» открывает старые записи, включая свои
для редактирования или удаления. Поиск для ответа проверяет весь общий пул.
Веса модели не меняются.

**Как проверить:** под первым пользователем завершите вопрос с характерными словами,
откройте «Общая память АС» и найдите новый автоматический кейс. Отметьте ответ «Не помогло»
и добавьте уточнение. Под вторым пользователем с доступом к тем же источникам задайте
похожий вопрос: запись первого пользователя появится среди использованной памяти,
её общий счётчик увеличится, а источники будут опрошены заново. Чат первого пользователя
при этом недоступен второму. После перезапуска запись и оценка сохраняются. Существующие
кейсы и подтверждённые записи автоматически доступны по общим правилам после обновления;
сброс SQLite не требуется. Старые чаты без записей памяти задним числом не импортируются.
Чтобы проверить обратную связь от повторного использования, оцените ответ второго
пользователя: у использованной записи первого изменится счётчик полезных или неудачных
применений. Повторное сохранение той же оценки не увеличит его ещё раз.

**Удаление чата:** удаляет запуск и связанные продолжения, их личные черновики,
обнаруженные ссылки и контрольные точки. Общий опыт и подтверждённые записи сохраняются,
ссылка на удалённый чат снимается. Автоматическая очистка старой истории действует так же.
Чтобы убрать общий опыт, автор удаляет запись отдельно в памяти; она перестаёт подбираться
для новых ответов всех пользователей. Активное исследование сначала нужно остановить.
При общей legacy-учётной записи история и возможность удаления также общие.

## LangGraph и продолжение исследований

Исполняемый `StateGraph`:
`prepare → plan → collect → inspect → decide → tools → reflect → decide`.
Из цикла возможен переход к итоговому `synthesize` или завершению.
Модель обновляет публичный план через `update_research_plan`, проверяет найденные
зависимости следующими поисками и чтениями, затем отмечает выполненные проверки и пробелы.
После набора действий `reflect` сравнивает материалы с предыдущим раундом.
Одинаковые вызовы без новых данных пропускаются; по умолчанию после трёх раундов без новых
материалов готовится итог с явным ограничением. Усилие ограничивает число раундов
бюджетом модели, инструментов и времени, а не специальной настройкой GigaCode.
Официальный `AsyncSqliteSaver` записывает контрольные точки между узлами и отдельными
вызовами инструментов (`durability="sync"`). В БД сохраняются данные состояния;
исполнители, ключи, текущая сессия и сигналы отмены туда не сериализуются.
План, найденные материалы и журнал действий входят в сохраняемое состояние.
При утрате доступа к источникам план скрывается вместе с ответом и журналом.

Чаты имеют устойчивый `conversation_id`. HTTP API: `GET /api/conversations`,
`GET /api/conversations/{id}?offset=0&limit=200`, `DELETE /api/conversations/{id}`.
Пути указаны относительно точки монтирования модуля (`/harness` в портале).
Сообщение отправляется прежним `POST /api/runs` с `parent_run_id` предыдущего ответа.
Удаление беседы учитывает всю сохранённую группу, даже если первый запуск уже удалён
по ретенции. Запоздавшие операции отменённого запуска не перезаписывают завершённый
результат, оценку или состояние нового продолжения.

Кнопка **«Продолжить с выбранными источниками»** повторно проверяет права и продолжает
планирование с оставшимся запасом вызовов модели и источников. Явное продолжение
получает новое окно времени той же длительности; общий счётчик длительности сохраняется.
Редакция профиля и потолки остаются прежними: для применения новых настроек создайте
новый запрос. Неопределённый результат прерванного инструмента
не воспроизводится автоматически; агенту требуется заново проверить состояние.
Песочницы создаются заново, прежние подтверждения из временной копии кода отбрасываются.
По умолчанию допускается до трёх продолжений; число меняется на странице управления.
После исчерпания бюджета нужен новый запрос.
Распределённая очередь и несколько реплик этим механизмом не добавляются.

## API модели и сертификаты

По умолчанию выбран **GigaCode**, использующий прежний исполнитель и вход. Во вкладке
**«Модель»** можно переключиться на совместимый с OpenAI Chat Completions API:
HTTPS base URL (например, `https://model.company/v1`) или полный endpoint
`https://model.company/v1/chat/completions`, таймаут и набор TLS-сертификатов.
Имя модели необязательно, если корпоративный шлюз выбирает модель по адресу.
При авторизации только сертификатами поле API-ключа оставьте пустым: заголовок
`Authorization` не отправляется. Если сервер требует Bearer-токен, укажите имя
серверной переменной окружения с токеном.
Кнопка проверки делает реальный короткий запрос генерации с текущими полями формы,
включая выбранные сертификаты, **до сохранения**. Она не меняет действующее подключение.
После успешной проверки сохраните настройки для переключения модели.
Смена провайдера запрещена, пока идут исследования.

TLS-набор содержит корпоративный CA и/или клиентский сертификат с соответствующим
приватным ключом PEM без пароля. CA дополняет системное доверие; проверка имени сервера
и сертификата всегда включена. Без набора используются системные CA. Приватные данные
хранятся отдельно в `tls-credentials` с правами `0700/0600`, в интерфейс возвращается
только описание. Перенаправления не выполняются. Поддерживаются корпоративные
`HTTPS_PROXY` / `NO_PROXY`; тестовый и рабочий запросы используют одинаковую настройку TLS.
Это API-адаптер указанного формата; другие протоколы моделей требуют отдельного адаптера.

Для личной истории сотрудников используйте `KB_ACCESS_ENABLED=true` с личными
учётными записями портала. Общий legacy token/пароль означает общую учётную запись,
а не 100 независимых сотрудников. В режиме без пароля доступ разрешён только локальному
клиенту как одному рабочему пространству разработки.

Дополнительные параметры из `agent_harness.config.HarnessSettings` имеют префикс
`HARNESS_`: workers каждой очереди, размер очередей, таймауты, лимит контекста и evidence,
срок хранения и число записей. По умолчанию хранятся до 100 завершённых запусков на
пользователя, до 10 000 всего, до 30 дней. SQLite и очереди рассчитаны на один процесс;
для нескольких workers/реплик нужны внешняя очередь и хранилище.

## Запустить отдельно

В этом репозитории можно запустить отдельный процесс, читающий настроенные индексы:

```sh
export HARNESS_API_TOKEN='<отдельный секрет не короче 32 символов>'
export HARNESS_STATE_DIR='./var/harness-standalone'
export HARNESS_PROVIDER_FACTORY='corporate_kb.harness_integration:standalone_providers'
PYTHONPATH=src .venv/bin/python -m agent_harness
```

Страница: `http://127.0.0.1:8020/`. Standalone-токен представляет одну общую учётную
запись. Для нескольких личных пользователей подключается собственный `authenticate`
к `create_app`. Не запускайте standalone и встроенный модуль с одним каталогом истории.

Для физического выделения в отдельный проект:

```sh
.venv/bin/python scripts/export-harness.py /tmp/independent-agent-harness
```

Команда создаёт новый каталог с `pyproject.toml`, документацией и только пакетом
`agent_harness`; существующий каталог не перезаписывается. Корпоративные адаптеры
не копируются. В отдельном проекте реализуются `SourcePort` и `ModelPort`, а доверенная
фабрика подключается через `HARNESS_PROVIDER_FACTORY`. Без неё страница запускается
с явным сообщением об отсутствии источников и модели.

## Проверка

```sh
PYTHONPATH=src .venv/bin/pytest -q tests/test_harness_runtime.py tests/test_harness_http.py tests/test_harness_integration.py tests/test_harness_integrations.py tests/test_harness_remote_tools.py tests/test_harness_sandbox.py
```

Проверки покрывают флаг выключения, отдельные маршруты и хранилище, реальный поиск
по тестовому RAG, границы пользователей, усилие и бюджеты, отмену, restart и HTTP.
Модель в тестах подменяется; проверки не подтверждают live-совместимость GigaCode.
