# Отдельный модуль «Харнес»

Харнес вынесен в `src/agent_harness`: собственная страница, HTTP API, настройки,
очереди, политика усилия, LangGraph и SQLite. Пакет не импортирует код портала, RAG
или GigaCode. Страница — самостоятельные HTML/CSS/JS без сборки dashboard.

Портал подключает его через один адаптер `corporate_kb.harness_integration`.
Адаптер передаёт авторизацию, доступ к текущим индексам и существующий исполнитель
GigaCode. Направление зависимости: **портал → адаптер → интерфейсы харнеса**.

Харнес и A2A используют один исполнитель GigaCode и его сохранённый вход. Страница
харнеса работает и при выключенном A2A. Дополнительный файл профиля GigaCode ей
не нужен. Инструкция запуска: [GigaCode](README.agent-activation.md).

## Подготовить или обновить одной командой

Из корня полученного репозитория:

```sh
./scripts/setup-harness.sh
```

Команда устанавливает библиотеки в `.venv` и заранее собирает два Docker-образа:
`harness-sandbox:local` для Git/SSH/Python/поиска и
`harness-sandbox-java21:local` с Java 21, `javac` и Maven. Повторный запуск использует
кэш Docker. Установка выполняется при подготовке сервера, а не на каждом вопросе.
Нужны **uv или Python 3.12**, работающий Docker Engine и доступ к реестрам при первой
установке. По умолчанию используется уже установленный uv; если его нет — обычный pip
через `scripts/setup-pip.sh --no-dev`. Сам uv скрипт не скачивает. Для pip нужен Python
3.12 или готовая `.venv` с Python 3.12; при наличии uv недостающий Python 3.12 может
быть установлен автоматически.

**Для корпоративной сети с настроенным pip, прокси или внутренним каталогом пакетов:**

```sh
./scripts/setup-harness.sh --installer pip
```

Этот режим сохраняет настройки pip, включая каталог пакетов, прокси и CA-сертификаты,
не подставляет публичный PyPI и работает даже при отсутствии пакета `uv` в каталоге.
Он устанавливает совместимые версии по ограничениям `pyproject.toml`, **не** точные
версии из `uv.lock`. Во внутреннем каталоге должны быть доступны зависимости проекта
и сборщик `hatchling`; отсутствие этих пакетов остаётся ошибкой установки.

Для точной установки из lock-файла используйте `--installer uv`: требуется уже
установленный uv. При ошибке этого режима скрипт завершится без скрытого переключения
на другой способ установки.

Только обновление библиотек, без сборки образов:

```sh
./scripts/setup-harness.sh --deps-only
# Корпоративный pip без uv:
./scripts/setup-harness.sh --installer pip --deps-only
```

Скрипт не делает `git pull`: сначала получите нужную версию репозитория, затем
запустите команду. В режиме uv используется полученный вместе с кодом `uv.lock`.
Он сохраняет ранее установленные дополнительные пакеты и не устанавливает тяжёлые
semantic extras. После обновления перезапустите backend. Подключения, `.env` и
включение песочниц остаются под управлением администратора в интерфейсе.

Отдельный сервер БД для первого запуска **не нужен**: SQLite создаёт файлы внутри
`KB_HARNESS_STATE_DIR`. Это общие файлы экземпляра, с отдельными записями пользователей.
Используйте постоянный локальный каталог на диске и один процесс backend; PostgreSQL
и распределённая очередь понадобятся при переходе к нескольким процессам/репликам.

## Включить или выключить

По умолчанию модуль выключен. В `.env`:

```dotenv
KB_HARNESS_ENABLED=true
KB_HARNESS_STATE_DIR=./var/harness
```

После перезапуска backend отдельная страница доступна на `/harness/`, а в навигации
собранного dashboard появляется ссылка «Харнес». Саму страницу харнеса собирать не нужно.
Она использует личную сессию портала. При старой схеме авторизации можно ввести Bearer
token или пароль администратора в форме страницы; данные остаются в текущей вкладке.

`KB_HARNESS_ENABLED=false` и перезапуск отключают страницу `/harness/`, её API,
собственные workers и создание её хранилища. Это не просто скрытие кнопки.
Агент A2A независимо использует общий runtime из пакета `agent_harness`;
эта настройка не отключает его и не запрещает импорт общего пакета.
При штатной остановке активные работы отменяются; история на диске сохраняется.
Следующее включение снова использует этот каталог. При аварии незавершённые работы
помечаются `interrupted`; доступно явное продолжение из сохранённого состояния LangGraph.

RAG-адаптер читает выбранные индексы и документы. В режиме исследования дополнительный
`ToolPort` подключает репозитории, исходящие MCP и A2A. Настройки и исполнители лежат
в самом `agent_harness`, без зависимости от основного dashboard. Личная память хранит
подтверждённые заметки и исправления; общая редакционная база знаний и MCP-вход к
харнесу пока не реализованы. Веса модели не переобучаются.

## Настройки репозиториев, MCP, A2A и песочниц

Кнопка **«Настройки»** доступна администратору. Настройки общие для экземпляра сервиса
и сохраняются в `KB_HARNESS_STATE_DIR/configuration.sqlite3` с правами `0600`; отдельная БД
под каждого сотрудника не создаётся. У подключения есть ID, название, включатель и
список серверных ID пользователей. Пустой список означает доступ всем вошедшим
пользователям Harness. В портале личный ID имеет вид `user:<id>`.

- **Репозитории:** HTTPS, `ssh://git@host/path` или `git@host:team/repo.git` и ветка,
  тег или commit. SCP-адрес сохраняет путь относительно домашнего каталога SSH-пользователя.
  При исследовании выбранного
  репозитория агент может клонировать его, искать текст, читать строки файлов и
  выполнять команды анализа/сборки/тестов в контейнере. Конкретный commit включается
  в подтверждения; HEAD не объявляется версией, развёрнутой в production.
- **MCP:** Streamable HTTP endpoint и явный список разрешённых инструментов.
  «Проверить» получает настоящий каталог, после чего администратор выбирает инструменты.
  Пустой список запрещает все вызовы. Агент читает схему выбранного инструмента;
  аргументы проверяются по текущей JSON Schema перед выполнением.
- **A2A:** JSON-RPC endpoint протокола 0.3. Проверка читает
  `/.well-known/agent-card.json` на том же origin; адрес из карточки не переопределяет
  сохранённый endpoint. Поддержаны `message/send`, ожидание `tasks/get` и попытка
  `tasks/cancel` при отмене. Удалённый агент получает только сформулированный вопрос.
  Его ответ обозначается как вывод другого агента, а не автоматически доказанный факт.
- **Доступы:** поле токена содержит **имя переменной окружения сервера**, например
  `HARNESS_JIRA_TOKEN`, а не сам токен. Значение передаётся только настроенному endpoint
  как Bearer; для Git — как HTTP Authorization. Адреса с паролями и query запрещены.
  Для соединения с токеном требуется HTTPS. Redirect не переносит credentials.
  stdio MCP и интерактивные OAuth-подключения здесь не поддержаны.

Во вкладке **«SSH-ключи»** администратор добавляет приватный ключ PEM/OpenSSH без
пароля и доверенные строки `known_hosts`, затем выбирает ключ у репозитория.
Проверка ключа сервера строгая: автоматического доверия неизвестному SSH-хосту нет.
Приватный ключ хранится отдельно в `ssh-credentials` (каталог `0700`, файлы `0600`),
не возвращается API и не включается в контекст модели. Он передаётся через stdin
только в tmpfs контейнера клонирования. Анализирующие контейнеры не получают ключ
или SSH-agent. Ключ, на который ссылается репозиторий, нельзя удалить до изменения настройки.

Старый `integrations.json` импортируется в БД один раз при первом запуске новой версии;
последующие изменения читаются из БД. Исходный файл остаётся для резервного восстановления.

## Обнаруженные ресурсы и запросы доступа

Ссылки из пользовательского вопроса и полученных материалов появляются в разделе
**«Обнаруженные»**. Адреса из сгенерированного ответа не считаются обнаружением.
Поиск ссылок не обращается по ним в сеть, не запускает инструмент и не расширяет права.
Ссылки с встроенными HTTP-паролями отвергаются, query и fragment не сохраняются.

Читатель нажимает **«Запросить доступ»**: адрес становится виден администратору в
списке запросов внутри Harness. Сам вопрос и текст документа при этом не передаются.
Администратор открывает заполненный черновик подключения, уточняет тип/адрес,
назначает доступы и сохраняет. Черновик изначально выключен и ограничен автором
запроса. После настройки подключения оно отображается как настроенное; пользователь
выбирает новый источник и продолжает исследование либо создаёт новый запрос.
Произвольная web-ссылка не становится автоматически MCP-сервером или репозиторием.

Сохранение настроек само не запускает внешние действия. Подключения появляются в
области поиска, права и включатели перепроверяются при каждом вызове. **Быстрый режим
использует только RAG**, не клонирует и не запускает MCP/A2A. В исследовании действия
ограничены выбранной областью, усилием, временем и числом вызовов. «Выбрать всё»
выбирает область до 1000 источников; это не обещание опросить каждый источник за один запуск.
MCP allowlist определяет допустимые операции, но не является транзакционным approval UI:
не добавляйте в общий allowlist разрушительные инструменты. Удалённый A2A-сервис
сам отвечает за ограничения собственных действий; локальный timeout не гарантирует
остановку удалённой системы, если она не поддерживает отмену.
Для MCP отмена прекращает локальное ожидание и закрывает соединение; установленный
SDK не отправляет `notifications/cancelled`, поэтому удалённая операция может продолжаться.

## Подготовка песочниц на сервере

Обычная подготовка — `./scripts/setup-harness.sh`: она сразу собирает базовый и Java 21
образы. Если библиотеки уже установлены, образы можно собрать отдельно:

```sh
docker build -t harness-sandbox:local -f src/agent_harness/sandbox.Dockerfile src/agent_harness
docker build -t harness-sandbox-java21:local -f src/agent_harness/sandbox.java21.Dockerfile src/agent_harness
```

Java-образ содержит JDK 21 и Maven, поэтому компиляция отдельных Java-файлов не требует
установки JDK во время исследования. Для сборки конкретного Maven-проекта заранее
добавьте его зависимости и плагины в собственный доверенный образ и настройте доступный
локальный Maven repository. Наличие Maven само по себе не означает, что зависимости
любого проекта уже загружены; команды анализа выполняются без сети.

В **Harness → Настройки → Песочницы** включите песочницы и проверьте базовую среду
`harness-sandbox:local`. В разделе **«Дополнительные среды»** проверьте профиль
**Java 21**: образ `harness-sandbox-java21:local`, профиль включён. Для Java-запроса
выберите **«Исследовать» → «Среда выполнения» → «Java 21»**. Базовый образ при этом
заменять не нужно: профиль задаёт среду отдельного исследования.
Образ автоматически не скачивается (`--pull never`). Если Engine/образ недоступен,
код не выполняется на хосте в обход контейнера. Для другой сборочной среды подготовьте
свой образ с Python 3, Git и OpenSSH client; необходимые зависимости должны быть в образе, поскольку
после клонирования команды работают без сети.

Каждый запрос получает собственные временные тома, привязанные к владельцу и
репозиторию. Рабочие файлы находятся в ограниченном tmpfs, контейнер запускается
не от root, без capabilities, с read-only корнем и лимитами CPU/RAM/PID/времени/вывода.
HOME, каталоги хоста и Docker socket внутрь не монтируются. Сеть есть только на этапе
клонирования; Git hooks, submodules и LFS не запускаются. Команды анализа выполняются
отдельно с `--network none`. По завершении или отмене контейнеры и тома удаляются;
в истории остаются ограниченные результаты и ссылки, а не вся копия репозитория.
После аварийного завершения процесса оставшиеся ресурсы с метками Harness требуют
очистки администратором; автоматический сборщик ресурсов между рестартами пока не заявлен.
Docker изолирует рабочий код, но GigaCode CLI остаётся отдельным доверенным процессом
хоста; его границы описаны в `README.agent-activation.md`.

## Режимы и усилие

- **Быстро:** ограниченный параллельный сбор источников и один итоговый вызов модели.
  Найденные материалы появляются до готовности объяснения. По умолчанию бюджет
  выполнения — 20 секунд после выхода из очереди; при его исчерпании начинается
  отмена провайдера, очистка которого может потребовать дополнительного времени.
- **Исследовать:** сбор, чтение документов, код и разрешённые внешние инструменты,
  затем итог. Пользователь видит действующий этап и может отменить работу.
- **Усилие:** низкое, обычное, высокое. Меняет лимиты обращений к источникам, контекста
  и шагов исследования, а также число и размер фрагментов даже при одном индексе.
  Это исполняемая политика сервиса, не неподдерживаемый
  `reasoning_effort` GigaCode. Высокое усилие не гарантирует правильность ответа.
- **Исследовать глубже:** новый связанный запуск с вопросом предыдущего разбора.
  Источники читаются заново; предыдущий ответ не считается подтверждённым фактом.

Очереди быстрых запросов и исследований разделены. Общие лимиты внешнего провайдера
при этом сохраняются: мгновенный свежий ответ через CLI не обещается. Токенный streaming
не реализован; страница опрашивает статус и показывает реальные готовые данные.

Без модели поиск работает: результат помечается частичным, показываются найденные
материалы и причина отсутствия синтеза. Вместо анализа не выводится имитация ответа.

## Включить GigaCode

Используются существующие `KB_GIGACODE_ENABLED=true` и `KB_GIGACODE_COMMAND` с рабочей
командой CLI, как при анализе в портале. После обновления перезапустите backend,
откройте `/harness/` с правами администратора и нажмите **«Включить GigaCode»**.
Если требуется вход, ссылка появляется в карточке модели только администратору.
После готовности можно отправить вопрос. Включение во вкладке A2A также делает
модель доступной харнесу: отдельный повторный запуск не нужен.

Кнопка выключения управляет общим исполнителем и останавливает его вызовы в обоих
модулях. Отключение самой страницы через `KB_HARNESS_ENABLED=false` не отключает A2A.
После перезапуска сервера исполнитель снова ожидает явного включения администратором;
сохранённая CLI-авторизация остаётся. Общие читатели видят состояние, но не URL входа
и события администратора.

`KB_HARNESS_MODEL_PROFILE_PATH` больше не используется страницей и не блокирует её,
даже если содержит старый неверный путь. Отдельный экспериментальный
`GigaCodeChatModel` для LangChain по-прежнему требует явно переданный проверенный
`launch_profile`. Границы обычного CLI-запуска описаны в инструкции GigaCode.
Настоящий корпоративный CLI в среде разработки отсутствует; live-вход проверяется
на сервере, где уже установлен GigaCode.

## Хранение и пользователи

История и личная память живут в `KB_HARNESS_STATE_DIR/runs.sqlite3`, контрольные точки
LangGraph — в `checkpoints.sqlite3`, настройки — в `configuration.sqlite3`, обнаруженные
ссылки — в `discoveries.sqlite3`. Это общие базы экземпляра с разграничением по владельцу,
а не отдельные базы на каждого человека. Запуски принадлежат
серверному `owner_id`; браузер не задаёт этот идентификатор. Чтение и отмена чужого
запуска возвращают 404. Отозванная личная сессия не даёт читать историю; права
повторно проверяются перед чтением источника и после него.

В текущем портале право читать RAG является общим для авторизованных пользователей;
новая система индивидуальных ACL документов здесь не создаётся. При исчезновении
доступа к индексу сохранённый ответ и его evidence скрываются.

**Память:** пользователь сохраняет полезную заметку, исправление или урок, редактирует
текст и явно подтверждает использование. При похожем вопросе выбираются до трёх
подтверждённых заметок по совпадению слов с учётом владельца, текущих прав и выбранных
источников. В контексте они отмечены как прошлый опыт, а не доказательство текущего
состояния системы. В ответе видно, какие записи использованы. Память можно выключить,
изменить или удалить; максимум 200 записей на пользователя, 10 000 на экземпляр.

Сбои инструментов создают ограниченные черновики уроков без сырых ошибок, секретов
и аргументов. Пользователь добавляет правильный способ решения и подтверждает запись.
Так исправления влияют на следующие запросы; ни каждый поиск, ни ошибочный ответ
автоматически не становятся знанием. Веса модели не меняются.

**Удаление чата:** удаляет запуск и связанные продолжения, их заметки памяти,
обнаруженные ссылки и контрольные точки. Активное исследование сначала нужно остановить.
При общей legacy-учётной записи история и возможность удаления также общие.

## LangGraph и продолжение исследований

Исполняемый `StateGraph`: `prepare → collect → decide ↔ tools → synthesize`.
Официальный `AsyncSqliteSaver` записывает контрольные точки между узлами и отдельными
вызовами инструментов (`durability="sync"`). В БД сохраняются данные состояния;
исполнители, ключи, текущая сессия и сигналы отмены туда не сериализуются.

Кнопка **«Продолжить с выбранными источниками»** повторно проверяет права и продолжает
планирование с оставшимся бюджетом. Неопределённый результат прерванного инструмента
не воспроизводится автоматически; агенту требуется заново проверить состояние.
Песочницы создаются заново, прежние подтверждения из временной копии кода отбрасываются.
Допускается до трёх продолжений; после исчерпания бюджета нужен новый запрос.
Распределённая очередь и несколько реплик этим механизмом не добавляются.

## API модели и сертификаты

По умолчанию выбран **GigaCode**, использующий прежний исполнитель и вход. Во вкладке
**«Модель»** можно переключиться на совместимый с OpenAI Chat Completions API:
HTTPS base URL (например, `https://model.company/v1`), имя модели, необязательное имя
серверной переменной с Bearer-токеном, таймаут и набор TLS-сертификатов.
Проверка отправляет короткий тестовый запрос только сохранённому адресу.
Смена провайдера запрещена, пока идут исследования.

TLS-набор содержит корпоративный CA и/или клиентский сертификат с соответствующим
приватным ключом PEM без пароля. CA дополняет системное доверие; проверка имени сервера
и сертификата всегда включена. Без набора используются системные CA. Приватные данные
хранятся отдельно в `tls-credentials` с правами `0700/0600`, в интерфейс возвращается
только описание. Перенаправления и неявные proxy-переменные не используются.
Это API-адаптер указанного формата; другие протоколы моделей требуют отдельного адаптера.

Для личной истории сотрудников используйте `KB_ACCESS_ENABLED=true` с личными
учётными записями портала. Общий legacy token/пароль означает общую учётную запись,
а не 100 независимых сотрудников. В режиме без пароля доступ разрешён только локальному
клиенту как одному рабочему пространству разработки.

Дополнительные параметры из `agent_harness.config.HarnessSettings` имеют префикс
`HARNESS_`: workers каждой очереди, размер очередей, таймауты, лимит контекста и evidence,
срок хранения и число записей. По умолчанию хранятся до 100 завершённых запусков на
пользователя, до 10 000 всего, до 30 дней. SQLite и очереди рассчитаны на один процесс;
для нескольких workers/реплик нужны внешняя очередь и хранилище.

## Запустить отдельно

В этом репозитории можно запустить отдельный процесс, читающий настроенные индексы:

```sh
export HARNESS_API_TOKEN='<отдельный секрет не короче 32 символов>'
export HARNESS_STATE_DIR='./var/harness-standalone'
export HARNESS_PROVIDER_FACTORY='corporate_kb.harness_integration:standalone_providers'
PYTHONPATH=src .venv/bin/python -m agent_harness
```

Страница: `http://127.0.0.1:8020/`. Standalone-токен представляет одну общую учётную
запись. Для нескольких личных пользователей подключается собственный `authenticate`
к `create_app`. Не запускайте standalone и встроенный модуль с одним каталогом истории.

Для физического выделения в отдельный проект:

```sh
.venv/bin/python scripts/export-harness.py /tmp/independent-agent-harness
```

Команда создаёт новый каталог с `pyproject.toml`, документацией и только пакетом
`agent_harness`; существующий каталог не перезаписывается. Корпоративные адаптеры
не копируются. В отдельном проекте реализуются `SourcePort` и `ModelPort`, а доверенная
фабрика подключается через `HARNESS_PROVIDER_FACTORY`. Без неё страница запускается
с явным сообщением об отсутствии источников и модели.

## Проверка

```sh
PYTHONPATH=src .venv/bin/pytest -q tests/test_harness_runtime.py tests/test_harness_http.py tests/test_harness_integration.py tests/test_harness_integrations.py tests/test_harness_remote_tools.py tests/test_harness_sandbox.py
```

Проверки покрывают флаг выключения, отдельные маршруты и хранилище, реальный поиск
по тестовому RAG, границы пользователей, усилие и бюджеты, отмену, restart и HTTP.
Модель в тестах подменяется; проверки не подтверждают live-совместимость GigaCode.
