## Ответ на четыре главных вопроса за минуту

**Как создаётся вектор?** Текст документа нормализуется и делится на структурные чанки. К чанку добавляются название и доступные метаданные. Текущий hash-провайдер выделяет слова и символьные триграммы, через SHA-256 выбирает координату и знак вклада, складывает их в массив и нормализует его длину. В проверенной конфигурации массив содержит 1024 float32-числа. Нейросетевой провайдер существует отдельно и сейчас не выбран.

**Как хранится вектор?** Строкой матрицы NumPy. Для N чанков получается матрица N × 1024. На диске она лежит в `embeddings.npy`; тексты и сведения о происхождении находятся отдельно в JSON. Один вектор занимает 4 КиБ без текста и служебных структур.

**Как работает поиск?** Вопрос кодируется совместимым провайдером, фильтры выбирают подходящие чанки, затем `matrix @ query` вычисляет сходство со всеми выбранными строками. После ранжирования MCP упаковывает выдержки и ссылки. Ответ формулирует подключённый LLM-клиент. Score не равен вероятности правильного ответа.

**Что здесь за база?** Собственный `InMemoryKnowledgeStore` на Python и NumPy, с файловым кешем NPY + JSON. Отдельной векторной СУБД в этом пути нет. Статический граф сервисов хранится отдельно в JSON и использует собственные алгоритмы.

## Мини-словарь перед техническим разбором

- **Чанк** — единица текстового поиска, фрагмент документа с метаданными.
- **Признак** — слово либо символьная триграмма, которая даёт вклад в hash-вектор.
- **D** — число координат одного вектора. **N** — число чанков. **M** — число чанков после фильтрации.
- **Матрица** — все векторы, расположенные строками. **Dot product** — сумма произведений соответствующих координат.
- **L2-норма** — длина вектора. **Cosine similarity** — косинус угла между двумя ненулевыми векторами.
- **Коллизия** — разные признаки попали в одну координату. Это не обязательно совпадение полного SHA-256.
- **mmap** — отображение файла в адресное пространство процесса. Это не обещание нулевого расхода RAM.
- **Retrieval** — отбор источников. **Generation** — формулирование ответа моделью по контексту.
- **Evidence** — сведения, позволяющие проверить происхождение вывода. Их наличие не доказывает вывод автоматически.
- **Confidence графа** — категория силы/происхождения оснований, а не откалиброванный процент.
- **MCP** — интерфейс вызова инструментов клиентом, не название алгоритма поиска или базы.
- **SSOT** — сводное описание сервиса. Оно может быть сгенерировано моделью и требовать проверки.

### В01. Что система делает с документом и вопросом в целом?

Индексация и поиск — два разных этапа. При индексации сервер читает документы, приводит их к общему текстовому представлению, выделяет небольшие структурные фрагменты — чанки — и получает для каждого чанка числовой вектор. Затем он сохраняет тексты, метаданные и матрицу векторов. Эту сравнительно тяжёлую подготовку не нужно повторять при каждом вопросе.

При поиске сервер кодирует только вопрос, сравнивает его вектор с уже сохранёнными векторами и выбирает подходящие фрагменты. MCP-слой сокращает их до выдержек и добавляет ссылки на источники. Подключённый LLM-клиент может использовать эти материалы при формулировании ответа.

Полезная формулировка для выступления: «Сначала мы подготавливаем поисковое представление документов, затем каждый вопрос сравниваем с этим представлением и возвращаем проверяемый контекст».

### В03. Что такое вектор в этой системе и что означает одна координата?

Вектор — упорядоченный массив чисел фиксированной длины D. В локальной конфигурации D=1024, поэтому для одного текста получается 1024 числа. Это не 1024 слова и не 1024 заранее названные бизнес-темы.

В hash-режиме координата является ячейкой, в которую алгоритм складывает вклад определённых слов и символьных фрагментов. Несколько разных признаков могут попасть в одну ячейку. Значение может быть положительным, отрицательным или нулевым. После нормализации значение отражает относительный вклад признаков, а не их исходное абсолютное количество.

В нейросетевом режиме координаты определяются обученной моделью. Код репозитория не присваивает им человекочитаемые значения вроде «платежи», «риски» или «клиенты». В обоих режимах полезно сравнивать весь вектор, а не объяснять отдельную координату как самостоятельный факт.

### В05. Зачем разбивать документ на чанки и как выбираются границы?

Один документ может описывать много несвязанных вопросов. Если представить его одним вектором, конкретный небольшой раздел может потеряться на фоне остального текста. В этом репозитории единицей поиска является чанк: фрагмент документа с собственным текстом и контекстом раздела.

Сначала парсер выделяет заголовки, обычный текст, списки, таблицы и fenced code blocks. В текущем парсере структурными заголовками считаются Markdown-уровни от H1 до H4. Затем блоки группируются по heading_path. При смене раздела текущая группа завершается. Когда добавление блока превышает целевой размер группы, создаётся следующий чанк.

Большая обычная проза дополнительно делится по предложениям, а слишком длинные предложения — по словам. При этом целевой размер не означает, что каждый чанк будет одинаковой длины. Есть короткие разделы, длинные неделимые блоки и объединение маленького последнего хвоста с предыдущей группой, если это допустимо.

### В06. Что означают 700, 900 и 80 токенов? Это токены языковой модели?

Нет. Чанкер использует SimpleTokenCounter: регулярное выражение считает группы букв/цифр/подчёркиваний и отдельные непустые знаки пунктуации. Это детерминированная приближённая мера размера текста, а не настоящий токенизатор Qwen или модели, которая будет отвечать пользователю.

Настройки по умолчанию: целевой размер чанка 700, hard_max 900, overlap 80. На практике 700 — ориентир для группировки, а 900 — ограничение для делимой прозы и объединения блоков. Код и таблицы специально не разрезаются, даже если превышают 900. Контекст, который добавляется в embedding_text, тоже увеличивает вход по сравнению с самим chunk.text.

### В07. Что делает overlap и почему соседние чанки не всегда пересекаются?

Overlap повторяет часть конца предыдущего чанка в следующем, чтобы мысль на границе не оказалась полностью оторванной от контекста. Но реализация повторяет целые смысловые блоки, а не ровно последние 80 токенов.

Алгоритм идёт по блокам предыдущей группы с конца и включает только такой хвост, который помещается в overlap_tokens. Если уже самый последний блок длиннее 80 условных токенов, хвост может оказаться пустым. Если повторённые блоки вместе с новым блоком превысят hard_max, overlap также отбрасывается. При переходе в другой heading_path текущая группа просто завершается.

Поэтому корректная фраза — «до 80 условных токенов перекрытия целыми блоками там, где это возможно», а не «любые соседние чанки обязательно имеют 80 одинаковых токенов». Повторение блоков увеличивает число сохранённых символов и может давать несколько похожих кандидатов одного документа; далее MCP ограничивает их число при упаковке ответа.

### В08. Почему text и embedding_text — разные поля?

Поле text содержит сам фрагмент документа. Поле embedding_text содержит этот же фрагмент вместе с поясняющей шапкой: Document, Section, Document type, Service, Domain, Authority. Пустые значения пропускаются. Именно embedding_text передаётся в embed_documents.

Это позволяет одинаково сформулированным абзацам из разных сервисов иметь различающееся поисковое представление. Например, фраза «проверка перед списанием» получает дополнительный контекст, если известно, что она находится в документе limits-service и разделе «Дневные лимиты».

### В09. Здесь есть два вида хеширования. Чем они отличаются?

Первый вид нужен для идентификации и контроля изменений. content_hash вычисляется из нормализованного текста документа и его metadata. document_id дополнительно включает относительный путь и source_id. chunk_id включает document_id, путь заголовка, позицию чанка, content_hash документа и хеш текста чанка. knowledge_hash характеризует набор документов и параметры чанкинга. Эти значения помогают определить, что поменялось и какой кэш можно использовать.

Второй вид — feature hashing для поиска. SHA-256 вычисляется отдельно для каждого слова или триграммы и определяет координату и знак вклада в вектор. Это не «хеш документа, используемый как семантический вектор».

У идентификатора важна точность совпадения: значение совпало или нет. У поискового вектора важна геометрическая близость: общие признаки могут внести вклад в одинаковые координаты, поэтому похожие тексты можно ранжировать.

### В10. Как точно работает HashEmbeddingProvider?

Алгоритм создаёт нулевой float32-вектор длины D. Текст переводится в нижний регистр, затем регулярное выражение выделяет слова. Для каждого слова создаётся признак с префиксом w:. Также к слову добавляются границы ^ и $, после чего извлекаются все последовательности по три символа с префиксом c3:.

Для каждого строкового признака f вычисляется SHA-256 от UTF-8. Первые восемь байтов интерпретируются как целое big-endian; остаток от деления на D задаёт координату. Младший бит девятого байта задаёт знак. Если бит равен 1, добавляется +1, иначе −1. Повторяющиеся признаки добавляются повторно.

Формально: j(f) = uint64_be(SHA256(f)[0:8]) mod D; s(f) = +1, если SHA256(f)[8] & 1, иначе −1; v[j(f)] ← v[j(f)] + s(f). После обработки признаков ненулевой вектор делится на L2-норму.

Обучения на корпусе, словаря частот и IDF-весов в этой реализации нет. Один и тот же текст при одинаковой размерности обрабатывается детерминированно.

### В12. Почему hash может находить похожие слова, но ошибаться со смыслом?

### В13. Что такое L2-нормализация и зачем она нужна?

Для вектора v=(v₁,…,vD) L2-норма равна:

‖v‖₂ = √(Σⱼ₌₁ᴰ vⱼ²).

Если норма больше нуля, нормализованный вектор вычисляется как v̂ = v / ‖v‖₂. Его длина становится приблизительно равной 1. Приблизительно — потому что float32 хранит конечную точность. Нормализация позволяет сравнивать направление векторов, уменьшив прямое влияние общего количества признаков: длинный текст не получает высокий score только из-за того, что в нём больше слов.

Она не решает все проблемы длины. Дополнительные слова всё равно меняют направление и относительную долю релевантных признаков. А два полностью пропорциональных вектора после нормализации совпадут, как в примере «кот» и «кот кот».

Hash-провайдер оставляет нулевой вектор нулевым, чтобы не делить на ноль. Нейросетевой провайдер считает нулевой результат модели ошибкой. Пустая строка и строка только из пунктуации могут дать нулевой hash-вектор; сервис запрещает пустой/пробельный запрос, но отдельной проверки «есть ли у вопроса словесные признаки» в нём нет.

### В15. Почему вопрос и документ могут иметь разную подготовку для нейросети?

Они выполняют разные роли: документ представляет знание, а вопрос задаёт, какое знание нужно найти. Нейросетевой провайдер учитывает это через query prompting. ### В21. Что даёт mmap и означает ли это, что большой индекс не занимает RAM?

При загрузке embeddings.npy вызывается np.load с mmap_mode='r'. Это отображение файла в память для чтения: процесс получает доступ к данным без обязательного создания второй полной копии матрицы при старте. Далее store сохраняет предоставленный массив, а не делает дополнительную явную полную копию.

Но mmap не отменяет использование RAM. Операционная система обслуживает страницы файла через память; проверки np.isfinite(matrix).all() обращаются к значениям всей матрицы. Документы и чанки из JSON загружаются в обычные объекты Python.

Кроме того, поиск использует выражение embeddings[candidate_indices] @ query. Индексация массивом номеров строк создаёт временную выборку, которая может быть почти такой же большой, как исходная матрица, если фильтров нет. При построении нового индекса сервис также создаёт новый np.empty(N,D).

Поэтому точная формулировка: «mmap уменьшает лишнее копирование исходной матрицы при загрузке; поиск остаётся вычислением над данными в памяти и требует отдельного бюджета RAM».

### В25. Что происходит при перестроении и можно ли назвать файловый кэш транзакционной базой?

### В26. Как вычисляется сходство вопроса и чанка?

После получения вектора вопроса q хранилище выбирает строки матрицы, прошедшие metadata filters. Затем выполняется scores = matrix @ q. Для каждой строки xᵢ получается скалярное произведение sᵢ = Σⱼ xᵢⱼqⱼ. Результат — массив из одного score на каждого кандидата.

Общая формула косинусного сходства:

cos(x,q) = (x · q) / (‖x‖₂ ‖q‖₂).

Когда оба ненулевых вектора заранее нормализованы до единичной длины, знаменатель равен 1, поэтому cosine = x · q. Эту подготовку делают встроенные embedding-провайдеры. Store отдельно проверяет размерность и конечность, но не нормализует произвольные переданные извне векторы повторно. При прямом вызове store с ненормализованными числами получится просто dot product.

Далее может применяться min_score, отбор top-k через argpartition и сортировка выбранных результатов по score. Скалярное произведение вычисляется для всех строк, оставшихся после фильтров; это точный полный перебор, а не приблизительный ANN-поиск.

### В27. Можно ли score=0.8 читать как «ответ верен на 80%»?

Нет. Score характеризует геометрическое сходство двух векторов, а не вероятность истинности найденного текста или будущего ответа. Для ненулевых нормализованных векторов математический cosine лежит между −1 и 1; вычисления float32 могут давать небольшую численную погрешность. Отрицательное число допустимо, в частности из-за знаков hash-признаков.

Высокое сходство означает, что поисковое представление чанка близко к вопросу. Чанк при этом может содержать устаревшее правило, ошибочную спецификацию или описание отрицания. Низкий score не доказывает, что нужного смысла нет: hash может не связать синонимы, а полезный фрагмент может быть смешан с большим количеством другого текста.

Параметр min_score — пользовательский порог отбора. По умолчанию он None, поэтому низкие и нулевые scores не отсекаются автоматически. Нельзя без измерений перенести один удачный порог с hash на Qwen или с одного корпуса на другой. Нулевой hash-вектор вопроса даст нулевые dot products и не обеспечит содержательного ранжирования.

### В29. Почему сначала находятся 12 кандидатов, а возвращаются до 3 результатов?

### В33. Что здесь за база, каковы ограничения масштаба и чем граф отличается от векторов?

Основной векторный store — собственный InMemoryKnowledgeStore: Python-структуры плюс NumPy-матрица, сохранённая в файловом кэше. В этом рабочем пути нет отдельной векторной СУБД, SQL-запросов, HNSW или FAISS. При N выбранных чанков и размерности D вычисление scores требует порядка N×D операций, а фильтрация метаданных перебирает чанки. Реальное время зависит от размера корпуса, памяти и численных библиотек; одного названия NumPy недостаточно для обещания фиксированной задержки.

Граф системы — другой набор данных. Он хранит узлы, рёбра и evidence из анализа исходников в JSON-снимках system_graph.json и service_map.json. Вопрос «где описано правило?» обслуживается текстовым retrieval, а вопрос «какие сервисы связаны?» — графовыми механизмами. ### Г02. Каков контракт алгоритма и как написать собственный?

### Г11. Что означает confidence? HIGH — это 95% точности?

Нет. Confidence — категориальная метка правила/происхождения, а не калиброванная статистическая вероятность. Доступны `DECLARED`, `HIGH`, `MEDIUM`, `LOW`, `UNRESOLVED`. Конкретный смысл надо читать вместе с matcher/extractor и evidence. Например, однозначный HTTP alias получает HIGH, единственный contract-only target — MEDIUM, неразрешённая цель — LOW либо UNRESOLVED.

### Г12. Что такое evidence и почему ссылке можно доверять не безусловно?

Evidence — структурированная запись: repository, optional commit, file, line, snippet, extractor и confidence. Узел или ребро хранит `evidence_ids`, а не просто красивую подпись. Это позволяет вернуться к источнику и увидеть, каким правилом извлечён факт. Поле commit допускает `None`, поэтому обещать закреплённый commit для абсолютно каждой записи нельзя.

Evidence повышает проверяемость, но не доказывает смысл утверждения автоматически. Существующая строка может быть недостаточной, код может не исполняться, конфигурация — относиться к другому профилю, snapshot — устареть. Нормальная процедура — проверить commit/дату, строку с контекстом, matcher и issues. Ссылка на source — средство проверки, не замена проверки.

### Г13. Как GigaCode проверяет или дополняет граф? Может ли модель выдумать связь?

GigaCode verifier — опциональное обогащение после статики. По умолчанию кандидаты — unresolved или LOW/UNRESOLVED зависимости; `verify_all` расширяет выбор. Ответ принимается через строгую JSON-модель, а не произвольный текст.

Предложенное evidence проверяется по файлу внутри repository root и номеру существующей строки; snippet читается заново из исходника. Для НОВОГО discovered edge дополнительно требуются известные source/target, target entrypoint нужного сервиса, совместимый контракт и evidence с обеих сторон. Это серьёзно ограничивает выдуманные новые связи.

Однако правила для ИЗМЕНЕНИЯ существующего ребра слабее: проверяются ID кандидата и известность target service, невалидные новые evidence отклоняются, но обновление может использовать уже имеющийся список evidence. Универсального требования «новое валидное evidence + точный target entrypoint» для каждого confirm/retarget нет. Проверка существования строки также не является автоматическим доказательством её смысла. Следовательно, «модель не может ошибиться благодаря evidence» — неверное обещание.

### Г14. Почему граф не показывает всё? Какие есть лимиты анализа?

### Г16. Что именно делает OpenSpec? Это алгоритм поиска или отдельная модель?

В этом репозитории OpenSpec — прежде всего источник документов из Git. ### Г17. Когда в индекс попадает текст, созданный моделью?

Это возможно. Помимо документов команд, предусмотрен SSOT-generation workflow. MCP tool `kb_generate_system_ssot` поддерживает подготовку, выдачу context/read_file и `submit`. При submit сервер записывает Markdown под `ssot/generated/<service>.md` внутри knowledge root и при `finalize` запускает index build. Если frontmatter отсутствует, добавляются metadata, в том числе `source_type=generated` и `review_status=draft`; если текст уже начинается с `---`, текущая функция оставляет его frontmatter как есть. ### Г20. Есть ли авторизация и ACL на документы? TLS достаточно?

TLS защищает канал, но не определяет, какие документы разрешено читать конкретному пользователю. В корпоративном HTTP-модуле bearer token опционален: отсутствие токена означает открытый доступ. Если токен задан, требуется длина не менее 32 символов и сравнение через `secrets.compare_digest`. Admin password отдельно опционален; без него `_admin_authorized` возвращает true. TLS здесь односторонний, клиентские сертификаты не проверяются.

Это общие секреты доступа, не реализованная модель индивидуальных пользователей, ролей и per-document ACL. Наличие service/domain/status-фильтра поиска не превращает его в авторизацию: фильтр выбирает данные, а ACL ограничивает то, что субъект в принципе имеет право увидеть. В отдельном `gigacode_graph` HTTP-сервере политика строже: bind вне loopback без сильного bearer запрещён. Эти два entrypoint-а нельзя смешивать.

Для защищённого применения потребуются выбранная модель доступа, изоляция сети, управление секретами, аудит и проверка enforcement на всех API. Это требования к внедрению, не заявление, что они уже выполнены кодом. Текущие `.env` и настройки развёрнутого стенда здесь не проверялись.

### Г22. Что происходит, если индексация зависла, упала или её отменили?

RAG index build выполняется в отдельном `spawn`-процессе. Worker читает совместимый live cache, но пишет staging cache. Runner отслеживает timeout/cancel, останавливает процесс и публикует результат только после успешного завершения. По умолчанию timeout интегрированного приложения — 600 секунд. Текущая публикация заменяет четыре файла последовательно через `os.replace`; это не одна ACID-транзакция всех файлов, поэтому не надо обещать crash-consistency уровня СУБД.

Source analysis тоже вынесен в disposable process, передаёт progress/checkpoints и ограничен hard timeout. При timeout может возвращаться последний доступный partial result; он должен оставаться отмеченным как частичный. При restart незавершённые catalog jobs помечаются failed, а не автоматически выдаются за успешно завершённые. Отмена не делает уже опубликованный частичный граф полным.

### Г24. Чем подтверждать работоспособность и производительность? «300+» уже испытано?

Наличие цели «300+ микросервисов» не доказывает измеренную нагрузку на таком масштабе. Для воспроизводимого доказательства нужны конкретный corpus, commit, число файлов/чанков/векторов, provider/dimension, железо, версии, режим cold/warm, concurrency и метрики качества/latency/RSS. Без сохранённого измерения корректно говорить «архитектура для этой задачи», а не «проверено выдерживает 300+».

В коде есть инструменты измерения. RAG `Evaluator` считает Hit@1/3/5: встретился ли ожидаемый document среди первых K результатов. Это не качество итогового ответа LLM, не полнота всех фактов и не гарантированная точность. Graph Lab хранит elapsed_seconds, peak process RSS, graph stats и validation на заранее заданных ожиданиях. `UsageTracker` хранит process-local агрегаты вызовов, результатов и оценочных context tokens без самих запросов/текстов; после перезапуска это не долговременный журнал аудита.

Для разработки предусмотрены `./scripts/dev.sh test`, `lint`, `typecheck`, `eval`. ### Г25. Есть автоматический ремонт алгоритмов? Модель сама меняет production-код?

Есть отдельный Graph Lab repair workflow, но это не автоматическое самопереписывание production при любой ошибке. `prepare-repair` формирует задачу по run; команда `debug repair ... --allow-write` явно разрешает запись в отдельном Git worktree. При успешном ответе модели, наличии допустимых изменений и требуемых experiment-документов запускаются автоматические проверки; результат — patch и validation. Для применения в текущую ветку нужна отдельная команда `debug apply-repair <patch> --yes`; код применения вызывает `git apply --check`, затем `git apply`, а не commit/push.

Не смешивать этот путь с `GigaCodeRunner.run_workspace_edit`: Graph Lab repair имеет собственный subprocess-код. Его exclude-list — `agent,web_fetch,web_search`; shell/write/edit здесь не исключены. Worktree изолирует изменения Git-ветки, но сам по себе не является OS sandbox и не запрещает процессу доступ к остальной файловой системе. Утверждение «во всех режимах модели запрещён shell» не соответствует этому workflow.

Показать можно так: «Мы вынесли алгоритм за контракт и добавили не только заменяемость, но и контур воспроизведения дефекта: case → run → объяснение пропуска → isolated repair → проверки → отдельное применение». При этом зелёные автоматические проверки не отменяют code review и оценку на представительном корпусе, а сама модель может предложить неправильный алгоритмический фикс.

## Приложение. Умножение матрицы на вектор без магии

Ниже учебная матрица с двумя координатами, чтобы всё можно было посчитать вручную. Это НЕ реальные hash-векторы корпуса: рабочая размерность в проверенной конфигурации равна 1024.

```text
Три чанка, D = 2:

      [  1.0   0.0 ]                  [ 0.6 ]
E  =  [  0.6   0.8 ]       q =        [ 0.8 ]
      [ -0.8   0.6 ]

shape(E) = (3, 2)          shape(q) = (2,)

E @ q = [ 1.0×0.6 + 0.0×0.8 ] = [ 0.6 ]
        [ 0.6×0.6 + 0.8×0.8 ]   [ 1.0 ]
        [-0.8×0.6 + 0.6×0.8 ]   [ 0.0 ]

shape(scores) = (3,)
```

Нормы всех трёх строк и запроса равны 1. Например, для второй строки √(0.6² + 0.8²) = √1 = 1. Поэтому произведения здесь равны cosine. Второй чанк совпадает с направлением вопроса и получает 1.0, первый получает 0.6, третий ортогонален и получает 0.0. При top_k=2 и без дополнительных ограничений порядок будет: второй чанк, первый чанк.

Если metadata filter исключил второй чанк, он не участвует в произведении и не может выиграть поиск даже с идеальным вектором. Если после ранжирования ограничение «один чанк на документ» исключило повторный фрагмент, итоговая выдача снова может отличаться от простого списка самых больших чисел. Это объясняет, почему нужно различать матричное ранжирование и MCP-упаковку.

Ровно такое умножение выполняется в [memory.py:96](/Users/artapr/Documents/confuence-mcp-rag/src/corporate_kb/stores/memory.py:96), только с настоящими векторами и выбранными индексами строк. Матрица поиска имеет размер «число чанков × число признаков». Это не матрица смежности сервисного графа и не обязательно квадратная матрица.

### Мини-демонстрация настоящего hash-провайдера

Следующая команда запускается из корня уже установленного репозитория. Она не читает документы, не загружает Qwen, не запускает сервер и не пишет индекс. Выводит только учебные строки и вычисленные для них числа. `PYTHONDONTWRITEBYTECODE` отключает создание bytecode-файлов.

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python - <<'PY'
import numpy as np
from corporate_kb.embeddings.hash_provider import HashEmbeddingProvider

provider = HashEmbeddingProvider(dimension=1024)
texts = ["кот", "кот кот", "коты", "собака"]
matrix = provider.embed_documents(texts)
query = provider.embed_query("кот")

print("matrix:", matrix.shape, matrix.dtype, matrix.nbytes, "bytes")
print("query:", query.shape)
print("nonzero:", [(int(i), float(query[i])) for i in np.flatnonzero(query)])
print("norms:", np.linalg.norm(matrix, axis=1))
for text, score in zip(texts, matrix @ query, strict=True):
    print(text, round(float(score), 8))
PY
```

Ожидаются shape `(4, 1024)`, dtype `float32`, 16384 байта матрицы, единичные нормы с возможной погрешностью float32 и scores примерно `1.0`, `1.0`, `0.44721359`, `0.18898225`. Ненулевые координаты запроса: 59, 318, 753, 771. Объяснение ненулевого сходства «кот» и «собака» дано в В12: совпала координата разных признаков, а не смысл слов.

Не подменяйте этим примером проверку качества на документах. В настоящем индексе провайдер получает `embedding_text` с заголовками и метаданными, и ранжирование идёт по другому набору текстов. Эта демонстрация объясняет механику, а не измеряет точность RAG.
