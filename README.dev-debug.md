# Dev-режим: запись проблем и исправления через GigaCode

Для работы через отдельный UI запусти `./scripts/dev-console.sh`.
Запись, логи, планы, проверки и управление циклом доступны в браузере;
подтверждения файловых правок остаются в нативном терминале GigaCode.
См. [инструкцию Dev Console](README.dev-console.md).

Режим работает в Git checkout на той машине, где установлены GigaCode и dev-зависимости проекта.
Он отделён от MCP и обычного сервера: сервер не получает возможность сам запускать модель или
менять свой код. Из обычного терминала разработчик записывает тестовый сеанс, затем запускает
управляемый цикл исправления. Поддерживаются Linux, macOS и WSL.

## Быстрый запуск

На машине с checkout нужны Python 3.12, `.venv` с dev-зависимостями и авторизованный GigaCode.
Скрипт ничего не устанавливает. При необходимости окружение готовится обычной командой
`./scripts/dev.sh install` или `./scripts/dev.sh install-pip`.

Проверить обнаружение CLI без обращения к модели:

```bash
./scripts/dev-debug.sh doctor
# Если бинарник называется иначе:
./scripts/dev-debug.sh doctor --gigacode /path/to/gigacode
```

Для нового сеанса с подробными ошибками запусти dev-backend в первом терминале:

```bash
./scripts/dev-debug.sh run --label "Ошибка клонирования репозитория со скиллами" -- ./scripts/start-backend.sh
```

`run` использует последнюю сессию или создаёт первую. Он запускает именно переданную команду,
записывает её stdout/stderr и включает `KB_DEV_DEBUG_CAPTURE=1` для дочернего процесса.
Если backend уже занимает порт, останови его обычным способом перед запуском нового экземпляра.
Прерывание `run` завершает запущенную им группу процессов. Для работы с существующим сервером:

```bash
./scripts/dev-debug.sh start --label "Проверяю клонирование скиллов"
```

`start` всегда создаёт новую сессию и читает существующие лог-файлы до Ctrl+C. Подробную причину
ошибки, которую старый процесс уже отбросил, восстановить нельзя: для неё нужен новый запуск с
dev-capture и повторение проблемы. `watch` возобновляет запись последней сессии.

Пока первый терминал записывает, тестируй dashboard. Во втором терминале:

```bash
./scripts/dev-debug.sh note "Skills → Проверить источник: ошибка. Ожидаю список найденных скиллов."
./scripts/dev-debug.sh fix --goal "Исправить ошибку проверки Git-источника скиллов; после повтора должен появиться список скиллов"
```

Если задача уже есть в label или note, достаточно `./scripts/dev-debug.sh fix`.
Для другой установки CLI передай `fix --gigacode /path/to/gigacode`.
У GigaCode остаются его обычная авторизация и доступ к модели на этой машине.
Это не подключение к удалённому GigaCode по SSH: скрипт запускается непосредственно там.

Третий терминал необязателен, но удобен для наблюдения:

```bash
./scripts/dev-debug.sh status --follow
```

Все команды кроме `start` по умолчанию используют последнюю сессию. При нескольких сеансах
указывай `--session <ID>`, который выводится при старте. `start` и `run` в разных терминалах
не нужно запускать одновременно для создания первой сессии: сначала создай её одним способом.
Также доступен короткий вход `./scripts/dev.sh debug <команда>`.

## Что происходит после «почини»

1. Скрипт фиксирует состояние исходников, собирает ограниченный пакет логов, показывает путь
   и передаёт пакет GigaCode. Запуск `fix` разрешает анализ логов и исходников через эту CLI.
   Если нужен предварительный просмотр, сначала выполни `bundle`, прочитай файл, затем `fix`.
2. Открывается обычный интерактивный GigaCode. Он читает код и диагностику, предлагает причину,
   шаги, точный список файлов, проверки и критерий успешного воспроизведения. Ты подтверждаешь
   сохранение `plan.json` штатным запросом CLI. Исходники на этапе планирования менять нельзя.
   Когда план готов, введи `/quit`, чтобы вернуться в скрипт.
3. Скрипт проверяет структуру плана и показывает его. Ты утверждаешь конкретный план.
4. Открывается GigaCode для выполнения плана. Каждую правку подтверждаешь непосредственно в CLI.
   Выбирай однократное разрешение; не включай `auto-edit`, `yolo` или «разрешать всегда».
   После правок снова введи `/quit`.
5. Скрипт показывает изменившиеся файлы и точные команды проверок. После твоего разрешения
   запускает их, записывает вывод и коды завершения. Команды не берутся из произвольного текста
   модели: план выбирает только заранее определённые проверки.
6. Если проверки упали, следующий круг создаёт новый пакет и новый план с учётом ошибок.
   Если проверки прошли, ты при необходимости перезапускаешь dev-сервер на обновлённом коде,
   повторяешь исходный сценарий и подтверждаешь результат. Только тогда статус становится `resolved`.

Завершение процесса GigaCode с кодом 0 не означает исправление. Неподтверждённое воспроизведение
остаётся `scenario_unverified`; отказ, Ctrl+C, ошибка авторизации или неподдерживаемая CLI
останавливают попытку. Никакие подтверждения скрипт за тебя не нажимает.

## Разрешения и границы

Запуск записи заранее разрешает сборщику создавать **диагностические артефакты** в
`.cache/dev-debug`. Исходники сборщик не исправляет. Команда `run -- ...` разрешает запуск именно
указанного процесса, который сохраняет своё обычное поведение, включая рабочие файлы сервера.
Запуск проверок разрешается отдельно: pytest исполняет код проекта и может создавать файлы.
Если подтверждать нужно вообще каждую запись ОС, включая логи, базы и кэши, такой сборщик
не подходит без дополнительной изоляции — штатные подтверждения GigaCode относятся к его tools.

Для правок используется `--approval-mode default`, реальный TTY и унаследованные stdin/stdout/stderr.
Headless и конвейер с подачей ответов не поддерживаются. Shell, другие агенты, web-инструменты
отключены; при наличии соответствующих флагов отключаются MCP-серверы и extensions. Известные
настройки автоматического разрешения записи и hooks блокируют запуск: скрипт объясняет конфликт,
но не переписывает пользовательские настройки. Нужные флаги проверяются по `--help` установленной
сборки, поскольку возможности форка могут отличаться. Собственная история/служебные файлы CLI
ведутся по обычным правилам этой CLI.
Если пользовательские `.gigacodeignore`/`.qwenignore` запрещают чтение `.cache/dev-debug`,
GigaCode не сможет прочитать пакет: измени это правило сам для dev-сеанса. Скрипт не обходит ignore.

Это контроль штатных разрешений GigaCode, **не песочница ОС**. Снимки контролируют доступные Git
исходники поддерживаемых типов: игнорируемые файлы, секреты, бинарные данные и внешняя файловая
система туда не входят. Точные пути плана проверяются; игнорируемые пути, `.env`, CLI-конфиги и
сам механизм dev-debug автоматически не исправляются. Несоответствие области плана, смена HEAD
или изменение исходников во время проверки приводит к остановке, а не к автоматическому откату.
Существующие незакоммиченные изменения сохраняются. Commit/push, установка пакетов и перезапуск
рабочего сервера в цикл не входят.

Официальное описание режимов подтверждения:
[команды GigaCode CLI](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/commands).

## Логи и артефакты

Автоматически читаются:

- `.cache/kb/runtime/mcp-http.log` — журнал фонового HTTP-сервера;
- `.cache/kb/job-logs/*.log` — журналы задач (`KB_JOB_LOGS_DIR` переопределяет каталог);
- ошибки задач из `.cache/skills-registry/registry.sqlite3`
  (`KB_SKILLS_REGISTRY_DIR` переопределяет каталог);
- stdout/stderr команды, запущенной через `run`;
- пользовательские наблюдения `note` и метаданные Git/хеши исходников.

Дополнительный файл или каталог задаётся через `start --log /path/server.log` либо
`watch --log /path/logs`; параметр повторяемый. Каталоги дают файлы `*.log`, отдельные пути
поддерживают `.log`, `.jsonl`, `.txt`. Пользовательские пути сохраняются для последующих пакетов.
Переменные каталогов должны быть экспортированы в терминале сборщика; `.env` он не читает.
SQLite открывается без записи и sidecar-файлов; ещё не checkpoint-нутые WAL-записи могут появиться
позже. Для точной причины сбоя используй dev-capture и stdout/stderr.

При `KB_DEV_DEBUG_CAPTURE=1` Skills Registry дополнительно пишет очищенный traceback,
исходную причину Git-ошибки, source/job ID и фазу `git`, `scan` или `publish`.
Обычные публичные ошибки API и production-поведение не меняются. Разбор `SKILL.md` остаётся
необходимой проверкой формата скиллов; теперь его ошибку можно отличить от ошибки клонирования.
Сборщик не перехватывает браузерную консоль, сетевые запросы браузера или скриншоты автоматически:
наблюдения из UI добавляй через `note`, воспроизводимые frontend-сбои — также в тесты.

В каталоге `.cache/dev-debug/sessions/<ID>/`:

| Файл | Что показывает |
| --- | --- |
| `session.json` | Текущий этап, цель, номер попытки, последнее время сбора и проверки |
| `events.jsonl`, `events.previous.jsonl` | Хронология, очищенные логи, вывод проверок |
| `bundle-NNN.json` | Неизменяемый диагностический пакет очередной попытки |
| `round-NNN/plan.json` | Предложенный моделью план |
| `round-NNN/approved-plan.json` | Утверждённый план и время разрешения |
| `round-NNN/before.json`, `changes.json` | Метаданные исходников до и после правок |
| `round-NNN/checks.json` | Команды, длительности, коды завершения и результаты проверок |
| `round-NNN/acceptance.json` | Подтверждение разработчиком исходного сценария |

Полный внутренний диалог GigaCode не перехватывается: он виден в его терминале и штатной истории.
Журнал режима сохраняет переходы, запросы, утверждённый план и проверяемые результаты.
`bundle` позволяет подготовить пакет без запуска модели, `status --json` показывает состояние.

Логи ограничены: 64 KiB на файл за проход, до 100 файлов, около 2 MiB истории событий с ротацией,
до 100 последних ошибок, до 512 KiB на пакет и до 20 пакетов на сессию. Пропуски из-за лимитов
фиксируются. Старые сессии автоматически не удаляются. Переменные окружения, `.env`, сертификаты
и файлы ключей целиком не собираются; известные токены, пароли и auth URL скрываются. Маскирование
не может распознать любой секрет; перед работой с чувствительными логами проверь отдельный `bundle`.

## Проверки и остановки

По умолчанию запускаются `lint` (Ruff без исправлений), `types` (mypy) и `skills` (тесты реестра,
MCP и HTTP). План может добавить `tests` (весь pytest) или `dashboard` (TypeScript без генерации
файлов). Для правок dashboard последняя проверка добавляется автоматически. Можно выбрать
обязательные проверки самостоятельно:

```bash
./scripts/dev-debug.sh fix --check lint --check types --check tests --max-rounds 5
```

По умолчанию лимит — 3 попытки, до 30 ходов GigaCode на фазу и 600 секунд на одну проверку.
Параметры: `--max-rounds` (1–10), `--max-turns` (1–100), `--check-timeout` (1–3600 секунд).
Лимиты модели/оплаты не обходятся. Отсутствие изменений, повторяющаяся ошибка проверки, новые
файлы вне плана и исчерпание лимита переводят сессию в `needs_attention` с причиной.

После остановки прочитай `status`, добавь `note` с новой информацией и повтори `fix --session <ID>`.
Это создаст новую попытку по текущему состоянию; старые утверждения не переносятся на новый план.
Можно продолжать наблюдение через `watch --session <ID>`. При аварийном завершении ОС последняя
фаза в `status` может остаться незавершённой; блокировка процесса освободится, новый `fix` начнёт
новую попытку. Две одновременные команды `fix` в одной сессии запрещены.

Цикл помогает довести исправление до проверенного результата, но не обещает исправить любую
ошибку: недоступный Git, отсутствующие права, сломанное окружение и неполные логи могут требовать
действий человека. В таких случаях он сохраняет доказательства и явно останавливается.
