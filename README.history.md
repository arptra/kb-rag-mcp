# История документов и возобновление индексации

Обычный serving-индекс содержит только текущие документы. Захваченные редакции,
их фрагменты и готовые embeddings сохраняются отдельно в SQLite-архиве
`KB_HISTORY_DIR` (по умолчанию `var/history`). Очистка `.cache` не удаляет историю.
Для каждого индекса используется отдельное пространство: `KB_HISTORY_INDEX_ID`
либо стабильный ключ из абсолютного пути каталога знаний.

## Идентификаторы и время

Ответы поиска, чтения документа и чтения чанка содержат:

| Поле | Значение |
| --- | --- |
| `page_id` | Стабильная логическая страница; Confluence: `confluence:<source_id>:<remote_page_id>` |
| `document_id` | Точный сохранённый документ; старые ссылки продолжают читаться после обновления |
| `revision_id` | Редакция источника/снимка, если предоставлена провайдером |
| `source_version` | Номер редакции источника в виде строки; может отсутствовать у локальных файлов |
| `source_updated_at` | Дата изменения страницы в источнике; не заменяется временем загрузки |
| `revision_updated_at` | Дата состояния снимка с учётом вложений; используется в `as_of` |
| `fetched_at` | Когда содержимое было получено сервером |
| `is_latest` | Принадлежит ли редакция текущему опубликованному состоянию |
| `history_baseline` | Источник не предоставил дату; редакция является исходной наблюдаемой точкой |

`metadata.status` остаётся бизнес-статусом документа (`current`, `deprecated` и т. п.).
Он независим от `is_latest`. Старый `kb_search` сохраняет фильтр `status=current`
по умолчанию. Новый поиск редакций по умолчанию не фильтрует бизнес-статус.

При изменении только вложения дата страницы может остаться прежней. Провайдер
передаёт `snapshot_updated_at`, учитывающий даты конкретных версий вложений;
он становится `revision_updated_at`. Перезапуск извлечения изображения не
должен подменять дату редактирования страницы.

## MCP: поиск и чтение

`kb_search` и `kb_search_index` работают с текущим serving-индексом. Новая функция
`kb_search_versions` принимает `index_id` (по умолчанию `default`), `query`,
`top_k` от 1 до 20, необязательный `page_id` и обычные фильтры
`service`, `domain`, `document_type`, `status`, `authority`, `source_type`.

Режимы `version_scope`:

- `latest` — по умолчанию. Поиск только текущих страниц до ранжирования.
- `history` — поиск по сохранённым редакциям по релевантности; среди найденных
  кандидатов текущие совпадения выводятся перед историческими. Каждый результат
  содержит свою дату и `is_latest`. Старое совпадение содержит компактную ссылку
  `latest_revision` на текущую страницу: `document_id`, `source_version`,
  `source_updated_at`, `revision_updated_at`. По этой ссылке можно отдельно
  вызвать `kb_get_document`. Это сохраняет историческое совпадение, даже когда
  оно релевантнее свежего текста и `top_k=1`; свежая версия не теряется из виду.
- `as_of` — последняя известная редакция каждой страницы на момент `as_of`.
  Требуется ISO timestamp; дата без времени означает начало суток UTC.

`updated_from` и `updated_to` ограничивают **дату изменения страницы в источнике**,
включительно. Документы без известной даты не проходят такой фильтр.
Временные параметры принимают ISO 8601; значения без зоны трактуются как UTC.
Дата `as_of` выбирает редакции до вычисления релевантности.
Старый результат `as_of` тоже содержит `latest_revision` для сравнения с текущим
состоянием. Если у страницы нет доступной опубликованной текущей редакции,
`latest_revision` равен `null`.

Примеры аргументов MCP:

```json
{"query":"правила платежей", "index_id":"team-docs"}
```

```json
{"query":"прежнее ограничение", "index_id":"team-docs", "version_scope":"history", "top_k":5}
```

```json
{"query":"правила платежей", "index_id":"team-docs", "version_scope":"as_of", "as_of":"2026-05-01T23:59:59Z"}
```

`kb_get_document` поддерживает два способа чтения:

```json
{"index_id":"team-docs", "document_id":"точный-id-из-результата"}
```

```json
{"index_id":"team-docs", "page_id":"confluence:team:123", "source_version":"7"}
```

Вместо `source_version` можно указать `as_of`; без обоих параметров возвращается
текущая страница. `document_id` и `page_id` взаимоисключающие. Для версии снимка
вложения, однозначно выбранной поиском, используйте точный `document_id`.
`kb_get_chunk` продолжает принимать точный `chunk_id`, в том числе архивный.
Оба инструмента сохраняют ограничение размера возвращаемого контекста.

Пользовательские managed tools поддерживают `version_scope`, `page_id`,
`as_of`, `updated_from`, `updated_to` в схеме аргументов и defaults.
Обычные существующие определения сохраняют поиск актуального состояния.

## Полнота истории и доступ

`coverage` нового поиска сообщает `known_since`, `revision_count`,
`has_baseline`, `pending_chunks` и предупреждение о неполноте.
`complete=false` намеренно: наличие нескольких снимков не доказывает, что
между опросами или до подключения сохранены все правки источника.
Исходный локальный документ без даты не считается существовавшим до времени
его первого наблюдения. Импортированные старые версии должны содержать
собственные даты и конкретные версии вложений; неизвестное не реконструируется.

Подтверждённая потеря доступа к странице скрывает её и архивные редакции
в поиске, списках и чтении по точным ID. Физический архив сохраняется;
восстановление доступа снимает блокировку. Сетевой сбой сам по себе не является
подтверждением удаления или потери доступа.

Исторический поиск читает SQLite порциями и хранит в памяти только ограниченный
набор кандидатов. Архив не загружается целиком в serving-процесс. При большой
истории поиск всё равно может занимать больше времени: это последовательное
ранжирование подходящих сохранённых фрагментов, не отдельный ANN-сервер.

## Индексация и устойчивость к прерыванию

Embeddings вычисляются порциями `KB_EMBEDDING_CHECKPOINT_BATCH_SIZE` (по умолчанию 32).
Каждая завершённая порция записывается транзакционно. Ключ checkpoint включает
точный embedding-текст и идентичность embedding-провайдера/модели. Изменение
метаданных, участвующих в embedding-тексте, не использует устаревший вектор.
Повторный запуск с переиспользованием продолжает с отсутствующих результатов;
пересборка после очистки serving-кеша также использует сохранённые checkpoints.
Незавершённая порция будет вычислена заново.

Сборочная матрица размещена в mmap-файле. Проверка конечности значений идёт
порциями, чтобы не выделять дополнительную полную матрицу в RAM. После сборки
serving-store открывает опубликованный `.npy` в режиме чтения.

Файлы нового кеша записываются в `generations/<id>/`; файл `CURRENT` переключается
атомарно только после подготовки полного набора. Прерванная сборка не заменяет
работающий serving-кеш. Worker также не активирует новые latest-указатели архива
до публикации и перезагрузки serving-снимка. Неактивные поколения остаются на диске;
при обслуживании можно удалить весь disposable кеш и пересобрать его из документов
и durable checkpoints. Не удаляйте `var/history` при очистке кеша.

Старый плоский кеш схемы 1 читается без потери точных ID и мигрирует в поколения
схемы 2 при следующей сборке. Его последняя доступная версия сохраняется как
baseline в архиве перед заменой. Уже утраченные до обновления версии восстановить
из старого кеша нельзя.

При первой загрузке старого кеша архив заполняется **до открытия HTTP-порта**.
После `Loaded ... chunks from cache` в логе появляются проверка архива и
`History migration: documents ...` / `History migration: chunks ...` с числом
обработанных записей, процентом и временем. Перенос использует готовые векторы
из кеша без вызова модели и записывает до 500 записей одной транзакцией через
одно соединение SQLite. Зафиксированные порции сохраняются при прерывании;
следующий запуск дополняет недостающие данные. После полного переноса повторный
старт пишет `import skipped`. Архиву нужно дополнительное место для содержимого
и векторов; исходный кеш перенос не удаляет.

В фоновых операциях `KB_INDEX_BUILD_NO_PROGRESS_TIMEOUT_SECONDS` (600 по умолчанию)
ограничивает период без сообщений о продвижении, а не общую длительность здоровой
сборки. `KB_INDEX_BUILD_OVERALL_TIMEOUT_SECONDS` задаёт необязательный общий предел.
События `discovering`, `loading`, `migration`, `chunking`, `embedding`, `history_embedding`,
`saving`, `complete`, `published` передаются в журнал операции. Отмена или timeout
сохраняет уже завершённые embedding-порции. Явный программный аргумент
`IndexBuildProcessRunner(..., timeout_seconds=...)` по-прежнему задаёт общий предел.
