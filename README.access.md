# Управление доступом по личным сертификатам

Модуль читает CN клиентского сертификата как идентификатор пользователя, выдаёт токены и
проверяет их по отдельной базе при каждом HTTP-запросе. Пользователь получает доступ
к MCP tools, JSON API и обычному дашборду `/admin`. Управление доступом вынесено в
`/access-admin` с отдельными административными учётными записями.

Режим включается явно через `KB_ACCESS_ENABLED=true`. До включения сохраняется прежний
режим сервера. Получение готового MCP-конфига в браузере через `/connect` и альтернативный
клиентский помощник с автоматическим сохранением токена описаны в
[README.access-client.md](README.access-client.md).

Локальный и боевой запуск по умолчанию используют `presented`: сертификат любого
издателя служит источником CN, а токен — пропуском. CA, срок и назначение клиентского
сертификата не проверяются приложением. TLS всё равно подтверждает владение закрытым
ключом. Это не проверка личности сотрудника: другой сертификат с тем же CN означает
ту же учётку, даже если ключ и издатель другие. Новый CN может зарегистрироваться
автоматически. Используйте сервис только там, где эта модель доступа допустима.

Для старого поведения с проверкой клиентского CA задайте явно
`KB_ACCESS_CLIENT_CERTIFICATE_MODE=trusted_ca`: один `KB_ACCESS_CLIENT_CA_FILE` теперь
не включает проверку CA. Серверный HTTPS-сертификат и его проверка клиентами от этой
настройки не зависят.

## Localhost с существующим сертификатом браузера

Если браузер уже использует корпоративный клиентский сертификат, доступ к каталогу
его ключей не требуется. При наличии актуальных зависимостей проекта запустите:

```bash
./scripts/start-mcp-http.sh local
```

Откройте `https://localhost:8443/connect` на том же компьютере. Локальный профиль
по умолчанию использует `presented`: запрашивает сертификат без ограничения по CA,
сохраняет TLS-проверку владения ключом и читает CN. Если сертификата нет, CN пустой
или в сертификате несколько CN, страница открывается, но выдача токена возвращает
HTTP 403. Срок, EKU и KeyUsage в этом режиме не служат проверками доступа.
Некорректный TLS, несовместимый алгоритм или отсутствие доказательства владения
ключом по-прежнему могут завершить соединение до HTTP.

Импорт тестового `client.p12` не нужен, если браузер уже предъявляет свой подходящий
сертификат. Серверный сертификат проверяется браузером отдельно. Если корпоративные
настройки уже разрешают тестовый HTTPS на localhost, менять их не требуется.
Сервер не меняет политики браузера и не может заставить его выбрать сертификат.
Браузер всё ещё может отказаться предъявлять просроченный или неподходящий сертификат
по собственным правилам, даже если сервер готов прочитать его CN.

После обновления старой `.venv` нужна новая Python-зависимость `pyOpenSSL`:

```bash
.venv/bin/python -m pip install -e .
```

Это установка в окружение проекта, без `sudo`, пакетов ОС и изменений браузера.
Сам обычный запуск ничего не скачивает. Для подготовки новой среды есть явный
флаг `--setup`, описанный ниже. При отсутствии доступа к источнику зависимостей
потребуется разрешённый внутренний источник пакетов или заранее подготовленная среда.

Строгую проверку только тестового CA можно включить отдельно:

```bash
./scripts/start-mcp-http.sh local --client-certificate-mode trusted_ca
```

Если Python находится на другом компьютере, localhost браузера не указывает на него.
Нужен разрешённый сетевой адрес или согласованный проброс порта. Проверки с программным
TLS-клиентом не заменяют проверку выбора сертификата в реальном управляемом браузере.

## Проверка на localhost одной командой

Из корня актуального репозитория запустите:

```bash
./scripts/start-mcp-http.sh local --setup
```

Серверный скрипт работает на Debian/Linux и macOS; на Windows запускайте сервер в
WSL. Браузер и MCP-клиент могут работать на Linux, Windows или macOS, в том числе
на другом компьютере. Нативный PowerShell-запуск сервера этим Bash-скриптом не поддерживается.

Флаг `--setup` подготавливает `.venv` с Python 3.12 и runtime-зависимости проекта.
Если подходящего Python нет, используется `uv`, который может скачать Python 3.12
в локальный каталог проекта. При необходимости сам `uv` устанавливается через
системный Python в отдельную bootstrap-среду `.cache/access-bootstrap`, не в системные
пакеты. Нужен доступ к источникам Python и PyPI; существующая `.venv` с другой версией
Python не удаляется и не перезаписывается. Последующие запуски не требуют `--setup`.
Системный Python не заменяется. Механизм загрузки описан в
[документации uv](https://docs.astral.sh/uv/guides/install-python/).

Если базовый Python не поддерживает создание venv, потребуется готовая среда или помощь
администратора. Скрипт не вызывает `sudo` и не меняет пакеты ОС. OpenSSL CLI, mkcert,
Homebrew, Node.js и Vite для тестового режима не
нужны: сертификаты создаёт `cryptography`, а UI уже собран в репозитории.

Команда создаёт отдельную песочницу `.cache/local-access/`: самоподписанный CA,
сертификат HTTPS-сервера для `localhost`/`127.0.0.1`/`::1`, личный сертификат с ключом
и защищённый паролем `client.p12`, случайные пароли администратора и P12, SQLite-базу
доступа и небольшой тестовый индекс. Индекс строится автоматически с провайдером `hash`.
Все параметры сервера задаются этим профилем; рабочий `.env` и переменные `KB_*`
игнорируются. Рабочие документы, индексы, tools, граф и база доступов не используются.
GigaCode, SSOT и Domscribe отключены. Песочница не меняет конфигурацию режимов `run`/`start`.

Без сетевых параметров сервер слушает только `127.0.0.1:8443`. Скрипт печатает адреса
`/connect`, `/admin`, `/access-admin`, `/mcp` и пути к сертификатам и файлу паролей.
Секреты не печатаются без явного флага. Для просмотра паролей и попытки открыть
диалоги импорта на компьютере с графической средой:

```bash
./scripts/start-mcp-http.sh local --open-certificates --show-secrets
```

`--open-certificates` — необязательная помощь: macOS использует `open`, Linux с
графической средой — доступный `xdg-open`. Импорт и доверие всё равно подтверждаются
вручную. На headless Debian флаг не останавливает запуск: скрипт печатает инструкцию
для клиентского компьютера. Не используйте `--show-secrets` при записи терминала или
отправке логов. Шаги импорта для разных ОС приведены ниже.

Повторные запуски используют те же сертификаты, пароли и базу: отзыв доступа сохраняется.
Пароли лежат в `.cache/local-access/identity/credentials.json` с правами `0600`,
каталог личных данных имеет права `0700`. CA-ключ после генерации не сохраняется.
При повреждённой, неполной или просроченной паре запуск остановится, не заменяя личность
и не сбрасывая базу. Для новой независимой песочницы выберите новый пустой каталог
через `--state-dir`, например `.cache/local-access-new`; затем импортируйте новый CA и P12.
Сертификаты пользователя и сервера действуют 30 дней. Не коммитьте и не пересылайте
весь каталог с ключами и паролями. Для переноса одной тестовой личности используйте
только специально подготовленный клиентский ZIP, описанный ниже.

Дополнительные команды:

```bash
# Другой локальный порт
./scripts/start-mcp-http.sh local --port 9443

# Подготовить файлы и посмотреть пароли, не запуская сервер
./scripts/start-mcp-http.sh local --prepare-only --show-secrets

# Справка
./scripts/start-mcp-http.sh local --help
```

Локальный сервер работает в текущем терминале; остановка — `Ctrl+C`. Он не использует
PID-файл обычного запуска, поэтому не останавливает существующий сервер. Если порт занят,
выберите другой через `--port`. При завершении эксперимента удалите доверие именно к этому
тестовому CA и импортированную личность в хранилище браузера/ОС.

## Debian сервер и браузер на другом компьютере

На сервере из корня репозитория выполните, заменив `192.168.1.10` на его IP или DNS,
доступный с клиентского компьютера:

```bash
./scripts/start-mcp-http.sh local --setup \
  --host 0.0.0.0 \
  --server-name 192.168.1.10 \
  --port 8443 \
  --show-secrets
```

`--host` задаёт адрес прослушивания. `0.0.0.0` разрешает входящие подключения по IPv4
на всех интерфейсах; для узкого доступа укажите конкретный IP интерфейса сервера.
`--server-name` — только DNS или IP без `https://`, порта и пути. Он включается в SAN
сертификата, используется в напечатанных адресах и клиентской инструкции. Для IPv6
укажите `--host :: --server-name 2001:db8::10`, заменив пример на реальный адрес.

Для сетевого имени по умолчанию используется отдельный каталог `.cache/network-access`,
чтобы не менять предыдущую localhost-песочницу. Сертификат включает указанный адрес и
localhost-имена. Повторите ту же команду без `--setup` для обычного запуска. Порт можно
менять; другой DNS/IP требует нового `--state-dir`, поскольку существующий сертификат,
CA, пользователь и блокировки не перевыпускаются автоматически.

Разрешите TCP-порт только для своего клиентского адреса или тестовой сети в firewall
сервера и сетевом firewall. Скрипт не меняет firewall, DNS или NAT. Это изолированный
тестовый стенд с автоматически созданной личностью, не production-развёртывание.

На сервере появится `.cache/network-access/client-import.zip`. В нём только:

- `ca.crt` — публичный тестовый CA;
- `client.p12` — зашифрованный личный сертификат вместе с его закрытым ключом;
- `README.txt` — адрес подключения и инструкция для клиентского компьютера.

В ZIP **нет** серверного ключа, административного пароля, пароля P12 или MCP-токена.
Перенесите ZIP по защищённому каналу на свой клиентский компьютер. Например, на клиенте:

```bash
scp user@192.168.1.10:/opt/kb-rag-mcp/.cache/network-access/client-import.zip .
```

Замените пользователя, IP и абсолютный путь на свои. Пароль P12 передайте отдельно
или возьмите из своего защищённого терминала сервера. Не переносите `server.key`,
`credentials.json` или весь каталог `.cache/network-access`. Этот тестовый сертификат
предназначен одному человеку: не раздавайте один ZIP всем сотрудникам. Сервер сохраняет
тестовую копию клиентского ключа; в production пользователи используют собственные
сертификаты и ключи согласно обычной схеме доступа.

Если у браузера нет подходящего существующего клиентского сертификата, на
**компьютере с браузером**, после распаковки ZIP:

1. Доверьте `ca.crt` для проверки HTTPS-сервера.
2. Импортируйте `client.p12` как личный сертификат с ключом, введя пароль P12.
3. Перезапустите браузер и откройте `https://192.168.1.10:8443/connect` с вашим адресом.
   Выберите личный сертификат и нажмите «Получить MCP-конфиг».
4. Для управления доступом откройте тот же адрес с `/access-admin`, логин `admin` и
   отдельный административный пароль из терминала сервера. После выдачи конфига здесь
   появятся пользователь, токен и события аудита.

`localhost` на другом компьютере обозначает **этот другой компьютер**, а не Debian-сервер.
Доверие CA требуется именно у браузера и MCP-клиента: установка CA только на сервере
не устранит клиентскую ошибку TLS. Готовый JSON не меняет TLS-настройки MCP-клиента.

### Импорт на клиенте с разными ОС

- **Windows, Chrome или Edge:** `ca.crt` импортируйте в хранилище текущего пользователя
  «Доверенные корневые центры сертификации», `client.p12` — в «Личное». Используйте
  мастер импорта сертификатов; не требуется копировать закрытый серверный ключ.
  [Хранилища сертификатов Windows](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/certificate-stores).
- **macOS, Safari или Chrome:** импортируйте CA в «Связку ключей» → «Вход» / login;
  в свойствах CA разрешите доверие для SSL. В эту же связку импортируйте P12 с ключом.
  [Настройка доверия в macOS](https://support.apple.com/guide/keychain-access/kyca11871/mac).
- **Linux или Firefox на любой ОС:** в менеджере сертификатов Firefox импортируйте
  CA в «Центры сертификации» для идентификации сайтов, P12 — в «Ваши сертификаты».
  Обычно менеджер находится в «Настройки» → «Приватность и защита» → «Сертификаты».
  У Chromium и других приложений может быть отдельное хранилище доверия.
  [Частные CA в Firefox](https://support.mozilla.org/en-US/kb/setting-certificate-authorities-firefox).

Если Linux-клиент использует системное хранилище Debian, CA можно установить отдельно
через `update-ca-certificates`; это не импортирует личный P12 и не гарантирует, что
каждый браузер/MCP runtime использует именно системное хранилище.
[Правила Debian для пользовательских CA](https://manpages.debian.org/bookworm/ca-certificates/update-ca-certificates.8.en.html).
Не отключайте проверку TLS. После эксперимента удалите доверие к этому тестовому CA
и импортированный личный сертификат с клиентского компьютера.

## Как проходит подключение

1. Клиент соединяется напрямую с Python-сервисом по HTTPS, предъявляя свой личный
   сертификат и подтверждая владение закрытым ключом в TLS-обмене. Ключ не покидает клиент.
2. В обычном режиме `presented` сервер получает сертификат непосредственно из
   TLS-соединения, а не из HTTP-заголовка или JSON, и извлекает ровно один непустой CN.
   Необязательный `trusted_ca` дополнительно проверяет цепочку, срок и назначение в TLS.
3. `POST /auth/mcp-config` из страницы `/connect` или `POST /auth/token` из клиентского
   помощника находит пользователя по CN. При первом обращении сохраняет CN,
   публичный сертификат и его метаданные в SQLite. Новый сертификат с тем же CN
   обновляет сведения последнего сертификата, но не создаёт другую учётку.
4. Если прежний токен из отдельной экспортной cookie браузера или Bearer-заголовка
   клиентского помощника действителен и принадлежит этому CN, сервер
   возвращает его же. Если токен отсутствует, истёк или неизвестен, сервер выдаёт новый.
   При отозванном пользователе выдачи не будет независимо от состояния токена.
5. Браузер показывает готовый MCP JSON для копирования или скачивания; пользователь
   переносит нужную запись в настройки клиента. Альтернативный клиентский помощник
   записывает её автоматически. Сервер не может сам редактировать настройки на чужом компьютере.
6. Каждый последующий запрос к MCP, JSON API или API дашборда проверяет живую запись
   токена, его срок/отзыв и статус CN-пользователя. Если запрос содержит сертификат
   с распознанным CN, он должен совпадать с владельцем токена. Без сертификата CN
   берётся из владельца токена в базе. Локального кэша разрешений нет.

Случайный Bearer-токен — не JWT и не хеш сертификата. Его нельзя вычислить по открытому
сертификату. В базе хранится только SHA-256 токена; полный токен возвращается клиенту.
Срок новых токенов задаётся `KB_ACCESS_TOKEN_TTL_SECONDS` независимо от срока сертификата.
Токены, выданные до обновления, сохраняют старый срок и автоматически не продлеваются.

CN нормализуется в Unicode NFC, пробелы по краям удаляются, регистр сохраняется:
`Alice` и `alice` — разные аккаунты. Управляющие символы и CN длиннее 256 символов
не допускаются. Fingerprint остаётся справочной характеристикой последнего сертификата,
но не участвует в идентификации пользователя или проверке токена.

В режиме `trusted_ca` любой действующий сертификат из указанного клиентского CA автоматически
допускается при первом обращении. Ручного согласования новых пользователей нет. Используйте
CA, выпускающий сертификаты именно для разрешённых сотрудников, а не общий набор публичных CA.
В `presented` поля CN/subject/issuer не удостоверяют сотрудника. Совпадение CN у чужого
сертификата позволяет получить токен существующей активной учётки. Блокировка CN действует
на все сертификаты с этим CN, но другой CN позволяет зарегистрировать новую учётку.

## Подготовка сервера

Не смешивайте серверные и клиентские сертификаты:

- серверный сертификат с корректным DNS/IP в SAN и его закрытый ключ;
- PEM-файл доверенных клиентских CA нужен только для необязательного `trusted_ca`;
- личный сертификат и ключ у каждого пользователя, а не одна общая пара на всех.

CA клиента и CA серверного сертификата могут быть разными. Закрытый ключ CA сервису
не нужен. Каталог `certs/` исключён из Git; личные ключи и `.env` в репозиторий не добавляйте.

После обновления кода в уже подготовленном окружении обновите зависимости проекта:

```bash
.venv/bin/python -m pip install -e .
```

Это не требует `sudo` или установки пакетов ОС. UI уже собран в `admin_dist` и
хранится в репозитории: Node.js/npm для такого запуска не нужны. Для новой среды
можно использовать `./scripts/setup-pip.sh --no-dev`; для воспроизводимой
dev-установки — `uv sync --locked`. Если вы сами меняли исходники UI, пересоберите его:

```bash
npm --prefix apps/dashboard ci
npm --prefix apps/dashboard run build
```

Задайте параметры в окружении процесса или `.env`. Пример значений для `.env`:

```dotenv
KB_ACCESS_ENABLED=true
KB_ACCESS_DB_PATH=.cache/access/access.sqlite3
KB_ACCESS_CLIENT_CERTIFICATE_MODE=presented
KB_ACCESS_BOOTSTRAP_ADMIN_USERNAME=admin
KB_ACCESS_BOOTSTRAP_ADMIN_PASSWORD=<замените на уникальный секрет длиной от 16 символов>
KB_ACCESS_TOKEN_TTL_SECONDS=2592000
KB_ACCESS_ADMIN_SESSION_TTL_SECONDS=28800
KB_MCP_TLS_ENABLED=true
KB_MCP_TLS_CERT_FILE=/etc/corporate-kb/server.crt
KB_MCP_TLS_KEY_FILE=/etc/corporate-kb/server.key
KB_MCP_HTTP_HOST=0.0.0.0
KB_MCP_HTTP_PORT=8443
```

Вставьте настоящий случайный пароль вместо плейсхолдера, например созданный командой
`openssl rand -hex 32`, и ограничьте права на файл настроек. В коде нет встроенного пароля.
TTL пользователя по умолчанию — 30 дней, административной сессии — 8 часов.

Рекомендуемая точка запуска, которая читает эти настройки напрямую:

```bash
.venv/bin/python -m corporate_kb.mcp.http_server
```

`scripts/start-mcp-http.sh run` и `start` используют тот же порядок настроек:
переменные окружения процесса, затем `.env`, затем defaults `Settings`. Скрипт не
перекрывает TLS-пути или host/port и не генерирует сертификаты. Без явного host сервер
слушает только `127.0.0.1`; для сетевого доступа на ВМ задайте `KB_MCP_HTTP_HOST`
явно и ограничьте доступ firewall. `stop`/`status`/`logs` не требуют загрузки TLS.

Без CA в режиме `trusted_ca`, без первого административного пароля, с неверной TLS-парой
или с отключённым TLS
защищённый сервер не запустится. Старые `KB_MCP_HTTP_BEARER_TOKEN` и `KB_ADMIN_PASSWORD`
не дают обходного доступа при `KB_ACCESS_ENABLED=true`.

Показанная конфигурация ВМ использует тот же режим `presented`, что и localhost.
В нём `KB_ACCESS_CLIENT_CA_FILE` не используется. Серверные сертификат и ключ
задаются через `KB_MCP_TLS_CERT_FILE`/`KB_MCP_TLS_KEY_FILE`; тестовые пути не подставляются.
Не переносите тестовую базу и пароли на ВМ. Для сохранения выданных боевых токенов
при обновлении сервиса сохраняйте боевую access-базу.

Замена серверного сертификата/ключа не меняет пользователей или токены в сохранённой
базе. Новый сертификат должен подходить для адреса сервиса и требований клиентов.
Перевыпуск клиентского сертификата с прежним CN сохраняет учётку и её токены, независимо
от нового fingerprint, ключа или CA. Смена client-CA в строгом режиме сама по себе не
отзывает Bearer-токены: для этого используйте управление доступом.

### Обновление существующей базы

База схемы v1 автоматически переводится в v2 одной транзакцией. Пользователи с одинаковым
нормализованным CN объединяются; их токены привязываются к самой ранней учётке, администраторы
и журнал сохраняются. Исходные записи объединённой группы сохраняются в
`legacy_user_identities`, соответствие старых ID отражается в журнале миграции.
Если хотя бы одна запись CN была заблокирована, объединённая учётка остаётся заблокированной,
а все её токены отзываются. Записи без однозначного CN остаются видимыми, но их Bearer-токены
не дают доступ. При ошибке миграция откатывается; база не удаляется и не пересоздаётся.
Сохраните защищённую резервную копию базы перед обновлением боевого сервиса.

## Работа администратора

Откройте `https://<сервер>:<порт>/access-admin` и войдите bootstrap-логином и паролем.
Личный сертификат для входа администратора не требуется. Сертификат самого сервера
должен быть доверен браузеру.

На странице доступны:

- пользователи: CN, статус, данные последнего сертификата, первое и последнее обращение;
- токены: безопасный префикс, владелец, выдача, последнее использование, срок и отзыв;
- администраторы: создание новых аккаунтов и отключение существующих;
- журнал выдачи и отзыва доступа, входов и административных изменений.

Отключить последнего активного администратора нельзя. При отключении администратора
его сессии перестают работать. Пароли хешируются scrypt с индивидуальной солью;
административная cookie имеет `Secure`, `HttpOnly`, `SameSite=Strict`, а изменения требуют
CSRF-токен. Неудачные входы ограничиваются по логину/IP и по IP.

Bootstrap создаётся только в пустой таблице администраторов. Изменение переменной пароля
после первого старта не меняет пароль существующего аккаунта и не восстанавливает
отключённого администратора. Автоматического сброса забытого пароля пока нет; создайте
резервного администратора заранее. Не удаляйте базу для сброса пароля: это уничтожит и блокировки.

Пользовательская и административная сессии независимы. Админский логин не даёт доступ
к документам и обычному дашборду, а пользовательский токен — к управлению доступами.
Для работы с документами администратору тоже нужен личный сертификат пользователя.

## Дашборд пользователя

Откройте `https://<сервер>:<порт>/admin`. Браузер должен предъявить личный сертификат
при TLS-соединении. Если он уже установлен корпоративными средствами, повторный импорт
и доступ к файлам ключей не нужны. Импорт необходим только при отсутствии личного
сертификата и если он разрешён политиками вашей организации.
Нажмите «Войти по сертификату»: страница создаст сессию через `/auth/browser-session`.
Токен хранится в защищённой HttpOnly-cookie, а не в localStorage.

Пользователь получает весь обычный функционал дашборда: индексы, управляемые tools и
существующие операции сервиса. Это не раздельные права на каждый индекс. Отдельная
проверка `KB_BENCHMARK_PASSWORD` для benchmark остаётся прикладным ограничением этого tool.

Для проверки сертификатного входа используйте собранный UI через Python HTTPS-сервер.
Vite dev proxy не передаёт серверу личный TLS-сертификат браузера.

## Выдача MCP настроек через браузер

На `/connect` пользователь получает готовый JSON без установки Python. Выдача запускается
кнопкой, а не при загрузке страницы. `POST /auth/mcp-config` требует проверенный личный
сертификат и совпадающий Origin; ни админская cookie, ни токен без сертификата этого не заменяют.
Адрес в конфиге указывает на тот же HTTPS-сервис с настроенным `KB_MCP_HTTP_PATH`.

Для экспорта выдаётся отдельный токен, не токен сессии дашборда. Его повторное использование
поддерживает cookie `__Host-kb-mcp-config` с `Secure`, `HttpOnly` и `SameSite=Strict`.
Endpoint повторно читает CN из TLS-сертификата и проверяет реестр перед возвратом конфигурации.
Выход из дашборда отзывает только его сессию; скачанный MCP-конфиг продолжает работать.

Ответ запрещено кэшировать (`Cache-Control: no-store`). Полный токен виден пользователю
в JSON после явной выдачи; страница не сохраняет его в localStorage/sessionStorage.
Это секретный файл, а не публичный пример настроек. Смена или истечение токена не
обновляет уже скачанный файл автоматически: нужно получить и перенести конфиг заново.

## Отзыв и восстановление

**Отозвать пользователя** — блокировать CN и все токены этой учётной записи.
Следующий запрос будет отклонён; повторная выдача с любым сертификатом того же CN запрещена.
Удаление токена из MCP-настроек не снимает блокировку.

**Восстановить пользователя** — разрешить новую выдачу по CN. Старые отозванные
токены не оживают; клиент должен подключиться заново.

**Отозвать один токен** — заблокировать только конкретное устройство или сессию.
С сертификатом, содержащим тот же CN, активный пользователь может получить другой токен.
Для полного запрета выбирайте отзыв пользователя.

Отзыв проверяется на входе каждого нового запроса, включая запросы существующей MCP-сессии.
Уже выполняющийся tool или уже открытый поток не отменяется автоматически.

Идентификатор здесь — CN, а не fingerprint и не кадровая запись человека. Блокировка
учётки действует на тот же CN независимо от перевыпуска сертификата. В режиме открытой
регистрации другой CN создаёт новый аккаунт; глобальный запрет человеку этим не обеспечивается.

## Хранение и границы реализации

Реестр доступа находится в отдельной SQLite-базе, по умолчанию
`.cache/access/access.sqlite3`. Это не векторная база: embeddings и индексы остаются
в прежних хранилищах. Таблицы содержат публичные сертификаты и статусы пользователей,
хеши токенов, администраторов, хеши сессий, счётчики неудачных входов и аудит.

На POSIX файл базы создаётся с правами `0600`, новый родительский каталог — `0700`.
Существующие права каталога не меняются. Базу и её резервные копии защищайте отдельно;
при восстановлении старой копии можно вернуть ранее отозванный доступ. Не очищайте эту
часть `.cache` вместе с кэшем RAG. Несколько процессов должны видеть один и тот же файл.
Для нескольких серверов нужна общая транзакционная БД, а не независимые SQLite-копии.

В режиме `trusted_ca` TLS использует `CERT_OPTIONAL`: отсутствие личного сертификата допускается для входа
администратора и работы по уже выданному Bearer. Предъявленный сертификат обязательно
проверяется; для выдачи токена сертификат обязателен. При обращении к MCP/API с сертификатом
и токеном их владельцы должны совпадать. Это не привязка токена к ключу на каждом запросе:
украденный Bearer действует до отзыва/истечения, поэтому его нужно защищать как пароль.

В `presented` прямой TLS-адаптер на pyOpenSSL запрашивает сертификат любого издателя,
не отключая TLS-подтверждение владения ключом. После рукопожатия приложение читает CN;
даты, EKU, KeyUsage и издатель не определяют доступ. Отсутствующий или неоднозначный CN
не даёт права на выдачу токена. Поддерживается HTTP/1.1 и MCP streaming/SSE,
но не WebSocket. Режим не означает доверие к HTTP-заголовкам с сертификатами.
Рукопожатие ограничено 10 секундами и 1 MiB входных данных, очередь ответа — 16 MiB
на соединение; большие ответы должны передаваться потоковыми частями. Это ограничение
очереди, а не общий предел размера streaming-ответа.

Доверие к `X-Client-Cert`, `X-SSL-Client-Verify` и `X-Forwarded-*` не используется. Для
direct TLS применяется `CertificateH11Protocol`; обычный внешний запуск Uvicorn без этого
адаптера не передаст сертификат приложению и не обеспечит выдачу токенов. В `presented`
используется `openssl_transport.py`, который нельзя оборачивать ещё одним stdlib TLS-слоем.
Стандартная строка Uvicorn может показывать `http://`, поскольку встроенный TLS Uvicorn
не используется; ориентируйтесь на напечатанный приложением адрес `https://`.
TLS-терминация
на reverse proxy этим режимом не поддерживается.

Не реализованы: PKI-проверка CRL/OCSP, OAuth discovery/refresh flow, права на отдельные
индексы/tools, аппаратные ключи в клиентском помощнике, автоматическое удаление старого
аудита и сессий. Текущий отзыв — постоянная блокировка в реестре приложения. Ограничивайте
сетевой доступ к сервису и контролируйте размер базы. Проверка издателя возможна только
при явном включении `trusted_ca` и настройке доверенных клиентских CA.
