# Агентский сервис для объяснения АС и разбора обращений

Это план развития существующего портала в общий сервис примерно для 100 сотрудников.
Он объясняет устройство всей автоматизированной системы или её части и исследует
обращения о неправильной работе. Первый рабочий контур читает источники и выдаёт
проверяемый ответ; изменение кода и внешних систем — отдельное последующее расширение.

**Статус:** адаптер `GigaCodeRunner` к интерфейсу модели LangChain — экспериментальная
реализация; локальные тесты с подменой CLI и интеграции с LangGraph / Deep Agents проходят.
Настоящий GigaCode в этой среде не установлен, live-проверка ещё не выполнена.
Страница `/agents/` использует Deep Agents SDK. Инструкции приведены в [README.agents.md](README.agents.md).
Описанные далее сквозные Jira/БД-интеграции, общая память, MCP-вход и промышленное
масштабирование остаются планом. Готовность для нагрузки 100 сотрудников пока не подтверждена.

## Что уже можно использовать

- RAG с несколькими индексами и источниками Confluence.
- Граф сервисов и evidence с привязкой к repository, commit, файлу и строке.
- `FeatureContextPlanner`, соединяющий граф и поиск по индексам нужных сервисов.
- `GigaCodeRunner`, управляющий ограниченными CLI-запусками и структурированным результатом.
- Существующие MCP/HTTP-интерфейсы, механизмы доступа и портал.

Подробности: [repository analysis](README.repository-analysis.md),
[repository graph](README.gigacode-graph.md), [MCP-доступ](README.access.md).
Реестр внешних MCP не следует считать готовым шлюзом выполнения всех их инструментов:
аутентификация, разрешённые операции и обработка результатов требуют отдельной проверки.

## Один runtime, два способа обращения

```text
Чат портала через HTTP ─┐
                       ├→ авторизация → служба запусков → workflow LangGraph
GigaCode/IDE через MCP ─┘                                  │
                  ┌───────────────────────────────────────┤
                  ↓                                       ↓
         общие знания и evidence                 разрешённые свежие данные
         Confluence / граф / код                  Jira / Drop / БД / telemetry
                  └───────────────────┬───────────────────┘
                                      ↓
                         ответ, источники, ограничения
```

HTTP и MCP должны вызывать одну службу и применять одинаковые правила доступа.
Предлагаемые операции: начать исследование, получить состояние/результат, продолжить
диалог, отменить запуск. Длинная операция сразу возвращает `run_id`; клиент получает
прогресс отдельно. Названия и пути этих операций пока не являются опубликованным API.

Обычный вызов `kb_search` не передаёт серверу весь разговор и последующий ответ клиента.
Полная история доступна для задач, выполненных этим runtime, либо при явной отправке
сообщений клиентом. MCP сам по себе не создаёт память диалога.

## Быстрый ответ, исследование и усилие

Следующая таблица описывает варианты пользовательских режимов для проектирования.

```text
[ Вопрос об АС или обращении…                              ]
[ ⚡ Быстро | 🔎 Исследовать ]  [ Усилие: Обычное ▾ ]  [ → ]
```

| Настройка | Что делает сервис | Что получает пользователь |
|---|---|---|
| Быстро | Один проход поиска по готовым индексам, карте сервисов и проверенным карточкам; при необходимости — ограниченный параллельный сбор свежих данных, затем один вызов модели | Краткий ответ с источниками и указанием того, что не удалось проверить |
| Исследовать | Последовательные проверки гипотез: документация, код, Jira, разрешённые БД и доступная диагностика; следующий шаг зависит от результатов предыдущего | Сначала краткая сводка доступных данных, затем обновления результатов и обоснованный разбор |
| Усилие: Низкое / Обычное / Высокое | Меняет бюджет источников, контекста, инструментов и, в исследовании, циклов проверки | Понятный выбор глубины проверки с предупреждением в описании настройки, что большее усилие может занять больше времени |

Режим задаёт алгоритм, усилие — бюджет внутри него. Высокое усилие в быстром режиме
не запускает скрытое длительное расследование и не увеличивает длину ответа само по себе.
Если данных не хватает, быстрый ответ показывает пробел и действие «Исследовать глубже».
В текущем пилоте переход сохраняет вопрос и создаёт связанный запуск; подтверждения
собираются заново. Повторное использование неизменившихся данных после проверки прав
и свежести — следующее улучшение. Смена настройки действует на следующий запуск; для текущего
доступна отмена с сохранением уже полученных результатов.

### Откуда берётся скорость

1. Заранее обновлять карточки сервисов и процессов, граф, индексы и проверенные решения
   по изменениям источников. Ключевые сведения уже готовы к моменту вопроса.
2. Точный повтор при совпадении области вопроса, среды, версий и прав может получить
   готовый проверенный ответ без генерации. Похожий вопрос использует прошлую карточку
   как источник; похожесть сама по себе не разрешает выдать чужой ответ целиком.
3. Поиск, граф и независимые внешние чтения запускать параллельно с ограничениями на
   источники. Поиск в быстром режиме маршрутизировать обычным кодом; не тратить отдельные
   вызовы модели на составление плана каждого простого вопроса.
4. Отдавать найденные фрагменты и ссылки по мере готовности, отдельно от итогового
   ответа. Показывать время проверки и отличать предварительную сводку от заключения.
   Подтверждение приёма запроса и анимация загрузки не считаются первым полезным ответом.
5. Держать отдельные очереди и резерв исполнения для быстрых запросов и исследований;
   ограничивать общий доступ к CLI/модели и MCP. Если они используют один upstream-лимит,
   резервировать и его, иначе разделение очередей не защитит быстрые ответы от задержки.

Нельзя обещать моментальный новый анализ неизвестной жалобы. Почти немедленно можно
показать готовые доступные сведения; свежие обращения к источникам и генерация требуют
времени. Даже подходящий сохранённый ответ не следует выдавать как текущее состояние,
если версия среды или актуальность источников не подтверждены. В таком случае он
помечается как ранее проверенный, а текущее состояние проверяется отдельно.

У нынешнего адаптера каждый модельный шаг запускает CLI и проверяет его версию;
JSON-решение доступно после завершения шага. `stream()` не выдаёт токены по мере генерации.
Текущая страница опрашивает HTTP API и показывает этапы и готовые источники, а завершённый
ответ — после готовности. SSE можно добавить позднее. Эта выдача не является token streaming.
Проверка на реальном GigaCode должна отдельно измерить время запуска, получения первого
полезного результата и полного ответа. Если CLI не укладывается в целевую задержку,
быстрый путь потребует проверенного долговременно работающего модельного endpoint;
GigaCode можно сохранить для исследований. Возможность такого endpoint пока не установлена.

### Контракт настроек и начальные бюджеты

Предлагаемые поля общей HTTP/MCP-службы: `mode: quick | investigate`,
`effort: low | medium | high`. Сервер отображает их на версионируемую политику и сохраняет
выбранные и применённые настройки в запуске. Клиент не задаёт произвольные лимиты,
CLI-флаги или дополнительные права. Неизвестные значения отклоняются. Повтор и
восстановление используют сохранённую версию политики.

Ниже — начальные **ограничения для пилота**, а не обещанная задержка или измеренная
пропускная способность. Один вызов инструмента — одно обращение к источнику; независимые
обращения могут выполняться параллельно. Ограничение шагов модели включает финальный
синтез; ошибочные попытки и повторы также расходуют бюджет.

| Режим / усилие | Вызовы модели, максимум | Вызовы инструментов, максимум | Одновременные обращения к источникам, максимум |
|---|---:|---:|---:|
| Быстро / низкое | 1 | 2 | 2 |
| Быстро / обычное | 1 | 4 | 2 |
| Быстро / высокое | 1 | 6 | 3 |
| Исследовать / низкое | 3 | 6 | 2 |
| Исследовать / обычное | 6 | 12 | 2 |
| Исследовать / высокое | 12 | 24 | 3 |

Дополнительно задаются ограничение контекста, срок ожидания в очереди, общий deadline и
таймауты источников. Их значения выбираются после замера CLI и источников. Бюджет общий
для всех дочерних агентов и повторов; `max_tool_calls` одного ответа адаптера и LangGraph
`recursion_limit` не заменяют это ограничение. Последний вызов модели резервируется для
синтеза; если deadline уже исчерпан, сервис возвращает собранные данные без новой генерации
и явно сообщает о незавершённой проверке. Отмена и deadline должны останавливать
активный subprocess, а не только прекращать ожидание в HTTP.

«Усилие» в первой версии управляет работой нашего сервиса. Нативный параметр рассуждений
GigaCode не подтверждён и не передаётся адаптером: нельзя добавлять фиктивный
`reasoning_effort` или сообщать пользователю, что модель применила его. Если CLI позже
предоставит проверенную настройку, она добавляется через отдельную проверку возможностей.
В интерфейсе исследования отображаются выполненные действия и найденные подтверждения,
например «Найдены 3 источника» или «Проверяется задача Jira», а не внутренний ход мыслей.

### Проверки перед включением режимов

- Измерять отдельно ожидание в очереди, время до первого полезного результата и полного
  ответа; собирать p50/p95 для холодного и повторного вопроса в каждом режиме.
- Нагрузить длинные исследования и убедиться, что быстрые запросы сохраняют выделенную
  ёмкость. Число зарегистрированных сотрудников не заменяет профиль одновременной нагрузки.
- Проверить недостаток данных, недоступный источник, устаревший кеш и отзыв доступа:
  быстрый режим не должен компенсировать скорость выдуманными фактами.
- Проверить повышение глубины без потери контекста, общий бюджет подзадач, отмену,
  deadline и одинаковое применение `mode`/`effort` в HTTP и MCP.

## Первая итерация: GigaCode как адаптер модели

Экспериментальный адаптер реализует интерфейс LangChain `BaseChatModel`. Он преобразует
сообщения и схемы доступных инструментов в запрос к `GigaCodeRunner` и принимает JSON
одного из двух видов: финальный ответ либо запросы вызова инструментов с аргументами.
Из результата формируется сообщение LangChain с текстом или `tool_calls`.

Инструменты исполняет **внешний runtime** после проверки имени, аргументов и прав.
Результаты возвращаются следующими сообщениями с соответствующими идентификаторами
вызовов. Список инструментов в prompt — данные для выбора, не разрешение CLI выполнять их.

Для этого режима необходимо отключить нативные инструменты GigaCode и унаследованные
MCP-подключения. Рабочая директория и конфигурация запуска должны быть изолированы от
пользовательского checkout. Если установленная версия CLI не позволяет обеспечить
такой режим, запуск отклоняется; одного текста «не используй инструменты» недостаточно.

Это адаптация агентского CLI к контракту модели, а не нативный GigaChat API. Каждый шаг
может запускать отдельный процесс и повторно передавать контекст. Совместимость CLI,
точность учёта токенов, стоимость и задержки пока неизвестны. Неподдерживаемые параметры
должны явно отклоняться или документироваться; нельзя имитировать их успешное применение.
Поток событий CLI также не равнозначен потоковой выдаче токенов модели.

**Контрольная точка:** синтетические тесты проверяют преобразование сообщений, JSON,
`tool_calls`, ошибки и ограничения. Отдельный live smoke test на установленном GigaCode
должен подтвердить цикл «выбор инструмента → внешний вызов → ответ», запрет внутренних
инструментов/MCP, отмену и timeout. Синтетический тест не подтверждает совместимость CLI.

### Подключение адаптера

Дополнительные зависимости устанавливаются отдельно от обычного RAG:

```sh
uv sync --extra agents --inexact
```

Модуль: `corporate_kb.agents.gigacode_model.GigaCodeChatModel`. Обычные импорты RAG
не загружают LangChain и Deep Agents. Поддержаны `invoke`, `ainvoke`, `bind_tools`,
`with_structured_output` через function calling. `stream` выдаёт целое завершённое
сообщение; токены оценочные, стоимость по ним не рассчитывается. Изображения, `stop`,
`temperature` и другие неподдержанные параметры отклоняются. Невалидный JSON или
неизвестный инструмент завершают шаг ошибкой; автоматического исправления ответа пока нет.

Пример сборки графа после подготовки проверенного профиля и разрешённых инструментов:

```python
from langchain.agents import create_agent
from langchain_core.tools import BaseTool

from corporate_kb.agents.gigacode_model import GigaCodeChatModel
from corporate_kb.config import Settings
from corporate_kb.gigacode_runner import GigaCodeModelProfile, GigaCodeRunner


def build_agent(
    settings: Settings,
    verified_profile: GigaCodeModelProfile,
    allowed_tools: list[BaseTool],
):
    model = GigaCodeChatModel(
        runner=GigaCodeRunner(settings),
        launch_profile=verified_profile,
        max_input_chars=250_000,
        max_tool_calls=16,
        cache=False,
    )
    return create_agent(
        model=model,
        tools=allowed_tools,
        system_prompt=(
            "Объясняй АС по найденным источникам. Указывай ссылки и версии. "
            "Отделяй подтверждённые факты от гипотез и неизвестного."
        ),
    )


# graph = build_agent(settings, verified_profile, allowed_tools)
# result = graph.invoke(
#     {"messages": [{"role": "user", "content": "Как обрабатывается платёж?"}]},
#     config={"recursion_limit": 12},
# )
```

Это пример встраивания, а не готовый HTTP-сервис. `allowed_tools` создаёт сервер:
каждая обёртка проверяет права пользователя и ограничивает результат перед передачей
модели. Адаптер не реализует авторизацию. В Deep Agents передаётся тот же объект
`model`; его дополнительные инструменты и backend требуют отдельной настройки.

`GigaCodeModelProfile` задаёт имя, точную строку версии CLI, неизменяемый tuple аргументов
и описание проверенной изоляции (`isolation_notes`). Профиль — доверенная конфигурация
развёртывания; пользователь чата его не задаёт. В `Settings.gigacode_command` указывается
проверенный launcher/wrapper, который отключает встроенные инструменты, наследование MCP,
hooks и постороннего контекста. Сам текст `isolation_notes` ничего не отключает.
Готовый профиль с предположительными CLI-флагами намеренно не поставляется: их поддержку
нужно проверить на установленной версии. Без профиля адаптер не запускает процесс.

Каждый вызов использует новый временный каталог и проверяет версию launcher. Событие
нативного инструмента прерывает запуск, но инструмент к этому моменту уже мог выполниться;
этот контроль не заменяет изоляцию launcher. Кеш LangChain отключён в адаптере: попадание
в него обходило бы проверку версии CLI. Кеш результатов на уровне приложения можно
вводить только с учётом пользователя, прав, среды и версий источников.

Локальные проверки без настоящей модели:

```sh
PYTHONPATH=src .venv/bin/pytest -q tests/test_gigacode_runner.py tests/test_gigacode_model_runner.py tests/test_gigacode_chat_model.py
```

В тестах выполняется настоящий граф LangGraph с `ToolNode` и настоящий
`create_deep_agent`; подменён только ответ runner. В отдельных тестах fake CLI проверяет
процесс, временную директорию, версию, отмену и отклонение нативных tool events.

## Общие знания и актуальное состояние

Сохраняем общий каталог `сервис ↔ repository ↔ Jira component ↔ документы ↔ схема БД`
с aliases, владельцами и подтверждениями. Граф и индексы обновляются по изменениям
источников и расписанию. Не анализируем все репозитории заново при каждом вопросе.

Для evidence нужны тип и ссылка источника, сущности, версия/commit, время получения,
среда, область доступа и степень подтверждения. Ответ должен отличать факт источника
от вывода модели; противоречащие документы не исчезают при объединении результатов.

«Как работает сейчас» требует выбранной среды и соответствия сервиса развёрнутому
commit/release. HEAD репозитория, закрытая Jira и наличие миграции не доказывают состояние
production. Без deployment inventory ответ ограничивается известными версиями кода
и документации и явно показывает, какие сведения о среде не подтверждены.

## Workflow объяснения и расследования

1. Определить цель, область АС, среду и временной интервал; выделить недостающие параметры.
2. Найти связанные сервисы, документацию и контракты; составить ограниченный план чтения.
3. Параллельно получить независимые подтверждения из разрешённых источников.
4. При противоречиях дочитать конкретный документ, файл, issue или диагностическое событие.
5. Сформировать ответ: что происходит, чем подтверждено, гипотезы и необходимые проверки.

Каждый запуск ограничен временем, числом шагов, размером контекста и вызовами инструментов.
Отказ одного источника даёт частичный результат с обозначенным пробелом. Тексты документов,
issues и логов считаются содержимым источников, а не инструкциями изменить права или план.

Для жалоб нужны время события, среда и доступные идентификаторы операции; для установления
причины могут потребоваться логи, трассировки, метрики, история релизов и feature flags.
**Доступность этих источников ещё не подтверждена.** Сначала составляем их инвентаризацию.
Без наблюдаемости сервис объясняет возможный механизм и проверки, не объявляет гипотезу
доказанной причиной. Прошлый похожий инцидент также не доказывает причину нового.

Для этого контура достаточно небольшого явного LangGraph workflow. Deep Agents следует
оценивать отдельно на длинных открытых исследованиях и принимать только при измеримом
улучшении результата относительно времени, стоимости и управляемости.

## Состояние, память и выполнение

Предлагаемое общее хранилище — PostgreSQL: диалоги, запуски, checkpoints, журнал вызовов
и записи памяти. Крупные артефакты и логи хранятся отдельно с теми же правилами доступа.
Отдельная БД на каждого сотрудника не нужна; сведения о системе не копируются в каждый чат.

Разделяем состояние запуска, личную историю и общую проектную память. Principal определяется
серверной авторизацией; `thread_id`, `project_id` и `run_id` не предоставляют доступ сами по себе.
Проверка прав действует при поиске, чтении истории, восстановлении запуска и выдаче памяти.
Отзыв доступа должен распространяться и на кешированные результаты.

В общую память попадают проверенные решения с provenance и сроком актуальности. Сырые логи,
персональные сведения и приватные обращения не публикуются в неё автоматически. Нужны
правила хранения, удаления и квоты для истории, checkpoints и диагностических материалов.

Практически каждый завершённый разбор может создать **черновик карточки**: симптомы,
область АС, подтверждённые факты, диагностические шаги, ссылки и версии источников.
После проверки карточка становится доступна сотрудникам с соответствующими правами.
При похожем вопросе она помогает выбрать источники и шаги проверки; изменившиеся факты
перепроверяются. Обновление исходного документа или релиза помечает связанные карточки
как требующие проверки. Поисковые запросы помогают находить пробелы в знаниях, но сами
не становятся фактами. Веса модели этим механизмом не обучаются.

LangGraph checkpointer сохраняет состояние workflow, но не заменяет очередь workers,
ограничение параллелизма, leasing, отмену процессов и восстановление после аварии. Текущие
catalog jobs после рестарта помечаются как interrupted/failed; продолжение агентских задач
необходимо реализовать и проверить отдельно. Повторы безопасного чтения ограничиваются.
Будущие внешние записи потребуют idempotency и сверки результата после неопределённого сбоя;
гарантия «ровно один раз» без поддержки внешней стороны не обещается.

## Этапы внедрения и критерии перехода

| Этап | Результат | Условие перехода |
|---|---|---|
| 0. Адаптер | Реализован, локальные проверки пройдены | Остались проверенный профиль launcher и live smoke test; ограничения CLI зафиксированы |
| 1. Источники и быстрый ответ | Каталог сущностей, evidence contract, параллельный сбор, разрешённые MCP-операции, один синтез | Сквозной вопрос связывает документацию, Jira и конкретный код; измерены полезный первый результат и полный ответ |
| 2. Сервис и исследование | Пилотный модуль HTTP уже выделен; далее MCP-вход, промышленное хранилище и восстановление | Оба входа применяют одну политику; быстрые ответы сохраняют ёмкость; ACL, бюджеты, отмена и restart проверены |
| 3. Жалобы | Доступные deployment/telemetry-источники и шаблон расследования | Реальные случаи отделяют подтверждённую причину от гипотез и неизвестного |
| 4. Память | Проверенные карточки разборов, поиск похожих случаев и переоценка актуальности | Повторный вопрос использует прошлый опыт; смена релиза и отзыв доступа не возвращают устаревшие или закрытые сведения |
| 5. Расширение | Постепенное подключение сотрудников и настройка ёмкости | Нагрузка и качество проходят согласованные измеримые пороги |

В этапе 1 сначала устраняем конкретные ограничения текущего поиска: в
`FeatureContextPlanner` — окно первых 200 документов и фильтрацию после top-k;
в связях источников — предположение об одном индексе на repository. Затем добавляем
выполнение выбранных внешних MCP tools поверх существующего initialize/list_tools.
Для первого сквозного сценария достаточно ограниченного набора: поиск документации,
чтение конкретного фрагмента кода и чтение связанной Jira. Общий произвольный SQL и
автономные изменения систем не являются необходимыми условиями этой итерации.

100 зарегистрированных сотрудников не означают 100 одновременных расследований. До выбора
ёмкости измеряем пик параллельных запросов, длительность шагов, лимиты CLI/модели/MCP,
размеры контекстов и рост хранения. По результатам задаём concurrency, очередь и квоты;
время ответа и число серверов без этих измерений не гарантируются.

Перед пилотом готовим эталонные вопросы по архитектуре и обезличенные завершённые обращения.
Проверяем подтверждаемость утверждений ссылками, охват нужных сервисов, обнаружение устаревших
данных, корректность при недоступном источнике и отсутствие утечек между пользователями.
Отдельные испытания: отозванные права, отмена активного subprocess, timeout, restart посреди
шага и нагрузка с одновременными лёгкими вопросами и тяжёлыми расследованиями. Порог качества
и целевые задержки согласуются после baseline; количество агентов не является метрикой успеха.
